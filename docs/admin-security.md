# 관리자 페이지 보안·개인정보 요건 명세

작성: 보안관 / 2026-09-09
대상 독자: 데이브(backend), 선우(frontend)
관련 문서: `docs/admin-ui.md`(수진), `docs/admin-architecture.md`(데이브)

이 문서는 **요건 명세**다. 구현 코드는 포함하지 않는다. 각 요건에는 ID와 우선순위,
그리고 "무엇을 확인하면 충족된 것으로 볼 수 있는지"를 붙였다. ID로 참조해라.

우선순위는 세 단계다.

- **필수** — 이 항목이 미충족이면 배포하지 않는다
- **권장** — 배포는 가능하나 다음 작업 사이클에서 처리한다
- **나중** — 지금 하지 않는다. 조건이 갖춰지면 재검토한다

법률 판단이 필요한 항목은 **[법률 검토 필요]** 로 표시했다. 나는 변호사가 아니고,
아래 조항 인용은 검증 대상이지 확정된 법적 조언이 아니다.

## 0. 먼저 — 이번 작업의 성격과 데이터 흐름

지금까지 이 사이트는 개인정보를 **한 건도 저장하지 않았다.** 상담 폼은
`ConsultForm.tsx` 안에서 클라이언트 검증을 하고 600ms 기다린 뒤 가짜 완료 화면을
띄우는 것이 전부였다. 이번 작업으로 그 폼이 실제로 이름과 연락처를 서버에 남기기
시작한다. 그 순간부터 개인정보보호법상 개인정보처리자의 의무가 실제로 발생한다.

### 0.1 데이터 흐름 (신뢰 경계 표시)

**상담 신청 (공개 · 미인증)**

```
브라우저 (익명 방문자)
  │  이름 · 연락처 · 희망시간 · 고민 · 동의 · 트랙(hidden)
  ▼ ══════════ 신뢰 경계 1 ══════════
Server Action (공개 엔드포인트. 누구나 POST 가능)
  │  ← 여기서 스키마 재검증 · 동의 확인 · 남용 방어 · 정규화
  ▼
저장소 어댑터 (지금은 JSON 파일)
  │
  ▼ ══════════ 신뢰 경계 2 ══════════
관리자 목록 화면 (인증 필요) → 대표만 열람
  │
  ▼
파기 (보유기간 경과 시 자동 + 수동)
```

**콘텐츠 편집 · 이미지 업로드 (인증 필요)**

```
브라우저 (대표)
  │  비밀번호 1개
  ▼ ══════════ 신뢰 경계 1 ══════════
로그인 Server Action → 서명된 세션 쿠키 발급
  │
  ▼ ══════════ 신뢰 경계 2 ══════════
proxy.ts (낙관적 차단) + 각 페이지/액션의 requireAdmin() (실제 차단)
  │
  ├─→ 콘텐츠 저장소 (JSON) → 공개 페이지가 읽어서 렌더
  └─→ 이미지 파일 저장 → 공개 URL 로 서빙
```

경계를 넘는 지점이 넷이다. 공개 폼 → 서버, 브라우저 → 로그인, 세션 쿠키 → 관리자
라우트, 업로드 파일 → 공개 서빙. 아래 요건은 이 네 곳에 검증을 세우는 것이 목적이다.

### 0.2 이 프로젝트 고유의 제약

- **Next.js 16.2.10.** `middleware.ts` 는 **`proxy.ts` 로 이름이 바뀌었고 middleware 는
  deprecated 다.** 함수명도 `proxy` 다. 이 차이가 요건 P1~P13 전체에 영향을 준다
- **배포는 Vercel 예정.** 런타임 파일시스템이 읽기 전용이다. JSON 파일 저장과 이미지
  업로드는 **프로덕션에서 동작하지 않는다.** 8절 참조
- **계정은 전부 신규 개설 예정이며 아직 없다.** Vercel WAF, Vercel Cron, Supabase,
  외부 캡차처럼 계정이 필요한 대응은 지금 검증할 수 없다. "권장"으로만 적었다
- **`AGENTS.md`: Supabase MCP 도구 호출 금지.** 이 문서를 쓰는 동안 호출하지 않았고,
  구현 단계에서도 호출하지 않는다
- **의존성 현황**: `zod` 없음, `sharp` 없음, `jose` 없음. 새 패키지가 필요한 요건은
  그렇다고 명시했다. 승인 없이 설치하지 않는다

## 1. 관리자 인증

### 1.1 위협 모델 — 환경변수 비밀번호 1개 방식

"환경변수에 비밀번호 하나"는 관리자가 한 명일 때 합리적인 선택이다. 다만 이 방식이
구조적으로 못 막는 것과, 싸게 막을 수 있는 것을 구분해야 한다.

| # | 위협 | 이 방식의 취약점 | 필수 대응 |
| --- | --- | --- | --- |
| T1 | 온라인 무차별 대입 | 로그인 엔드포인트가 공개. 서버리스라 시도 횟수 공유 카운터가 없다 | AUTH-9 (비밀번호 엔트로피), AUTH-10 (고정 지연), AUTH-11 (인스턴스 카운터) |
| T2 | 비밀번호 재사용·유출 목록 대조 | 계정이 하나뿐이라 뚫리면 전부 뚫린다. MFA 없음 | AUTH-9 (사람이 만든 문구 금지, 난수 생성) |
| T3 | 환경변수 값 유출 (로그·에러화면·클라이언트 번들·대시보드) | `NEXT_PUBLIC_` 오접두어 한 번으로 번들에 박힌다 | AUTH-1, AUTH-2, AUTH-14 |
| T4 | 세션 값 위조 | 서명이 없으면 쿠키에 `admin=true` 만 써넣어도 통과한다 | AUTH-4, AUTH-5 |
| T5 | 세션 탈취 (XSS · 평문 전송) | 쿠키를 JS가 읽을 수 있으면 XSS 한 번에 세션이 넘어간다 | AUTH-6, HDR-1, HDR-7 |
| T6 | 세션 무효화 불가 | 서버측 세션 저장소가 없으므로 발급된 토큰을 개별로 취소할 수 없다 | AUTH-7 (짧은 만료), AUTH-8 (일괄 무효화 스위치) |
| T7 | CSRF | 관리자 쿠키가 붙은 상태에서 외부 사이트가 변경 요청을 유발 | CSRF-1, AUTH-6 (SameSite=Strict) |
| T8 | 타이밍 공격 | 문자열 `===` 비교는 일치 접두어 길이만큼 시간이 달라진다 | AUTH-3 |
| T9 | 피싱 | 비밀번호 1개 + MFA 없음. 대표가 가짜 로그인 화면에 입력하면 끝 | 기술적 대응 없음. AUTH-8 이 사후 수단 |
| T10 | 개발환경 비밀번호가 프로덕션과 동일 | `.env.local` 이 실수로 커밋되거나 화면 공유로 노출 | AUTH-13 |
| T11 | 로그인 시도 자체를 이용한 서비스 거부 | 계정 잠금을 넣으면 공격자가 유일한 계정을 잠글 수 있다 | AUTH-12 (잠금 금지, 지연으로만 대응) |

T9는 이 방식으로 막을 수 없다. 솔직하게 남긴다. 관리자에서 다루는 정보의 민감도가
올라가면(예: 상담 이력 누적) MFA 있는 인증 수단으로 옮기는 것을 재검토해야 한다.

### 1.2 비밀번호 저장과 비교

**AUTH-1 (필수) — 환경변수에는 평문 비밀번호를 두지 않는다. 해시만 둔다.**

환경변수 이름은 `ADMIN_PASSWORD_HASH` 다. 형식은 자체 정의한 단일 문자열로 한다.

```
scrypt$<N>$<r>$<p>$<salt_base64>$<derivedKey_base64>
```

권장 파라미터는 `N=16384, r=8, p=1`, salt 16바이트 난수, derivedKey 32바이트다.
Node 표준 라이브러리 `node:crypto` 의 `scrypt` 로 충분하다. **새 패키지가 필요 없다.**
`bcrypt`/`argon2` 는 네이티브 빌드가 필요해 서버리스에서 다루기 번거롭다. 굳이 쓰지 않는다.

평문 대신 해시를 두는 이유는 세 가지다. Vercel 대시보드 화면에 평문이 보이지 않는다.
빌드 로그나 에러 덤프에 값이 섞여도 즉시 재사용할 수 없다. 그리고 값이 salt 를 포함하는
한 문자열이라 관리 실수(공백·따옴표)가 검출된다.

> 검증: `ADMIN_PASSWORD` 라는 이름의 환경변수가 코드 어디에도 없다.
> `process.env` 참조를 전부 나열했을 때 평문 비밀번호를 읽는 지점이 0개다.

**AUTH-2 (필수) — 인증 관련 환경변수에 `NEXT_PUBLIC_` 접두어를 붙이지 않는다.**

`NEXT_PUBLIC_` 이 붙은 값은 클라이언트 번들에 문자열로 인라인된다. 실수 한 번이
비밀번호 해시를 전 세계에 배포하는 결과가 된다.

> 검증: `next build` 후 `.next/static` 전체에서 `ADMIN_`, `SESSION_SECRET`,
> `scrypt$` 문자열을 검색해 0건. 이 검색을 배포 전 체크리스트에 넣는다(7절).

**AUTH-3 (필수) — 비밀번호 비교는 타이밍 안전하게 한다.**

입력 비밀번호를 저장된 salt·파라미터로 다시 scrypt 파생시킨 뒤, 32바이트 버퍼끼리
`crypto.timingSafeEqual` 로 비교한다. 문자열 `===` 나 `==` 를 쓰지 않는다.

`timingSafeEqual` 은 **길이가 다르면 예외를 던진다.** 파생키는 항상 32바이트라 문제가
없지만, 비교 직전에 `length` 를 확인하고 다르면 예외 대신 `false` 를 반환해라. 예외가
그대로 올라가면 에러 화면에 스택이 노출될 수 있다.

> 검증: 로그인 처리 경로에 비밀번호를 다루는 `===`/`!==`/`.includes` 가 없다.

**AUTH-14 (필수) — 필수 환경변수가 없거나 형식이 깨지면 fail-closed 한다.**

`ADMIN_PASSWORD_HASH` 또는 `ADMIN_SESSION_SECRET` 이 비어 있거나 파싱에 실패하면
**모든 로그인 시도를 거부**하고 모든 관리자 라우트를 차단한다. 절대로 "설정이 없으면
인증을 건너뛴다"로 만들지 마라. 그 분기가 프로덕션에 남으면 관리자가 무인증 공개된다.

기동 시 경고 로그를 남길 때 **값을 찍지 않는다.** `ADMIN_SESSION_SECRET is not set`
까지만 쓴다. 길이·앞자리·해시도 찍지 않는다.

> 검증: 환경변수를 비운 상태로 `/admin` 접근 시 로그인 화면 또는 404 가 나오고,
> 콘텐츠나 상담 목록이 절대 렌더되지 않는다.

### 1.3 세션 토큰

**AUTH-4 (필수) — 세션 값은 서명한다. 쿠키에 담긴 값을 신뢰하지 않는다.**

토큰 형식을 다음으로 고정한다.

```
v1.<payload_base64url>.<hmac_base64url>
payload = JSON: { "iat": <초>, "exp": <초>, "pv": "<16자 hex>" }
hmac    = HMAC-SHA256( key = ADMIN_SESSION_SECRET, msg = "v1." + payload_base64url )
```

`ADMIN_SESSION_SECRET` 은 32바이트 난수의 base64 다(`openssl rand -base64 32`).
`ADMIN_PASSWORD_HASH` 와 **다른 값**이어야 한다. 같은 값을 두 용도로 쓰지 않는다.

JWT 를 쓰지 않는 이유는 알고리즘 혼동(`alg: none`, HS/RS 혼용) 취약점 표면을 아예
만들지 않기 위해서다. 형식이 고정되면 파서가 선택할 여지가 없다. `jose` 를 쓰고 싶다면
`algorithms: ['HS256']` 을 명시적으로 고정해야 하고, 그러면 패키지 추가 승인이 필요하다.
표준 라이브러리로 되는 일에 의존성을 늘릴 이유가 없다.

**AUTH-5 (필수) — 검증 순서를 지킨다. 서명 검증 전에 payload 를 파싱하지 않는다.**

1. 문자열이 `v1.` 로 시작하고 점 2개로 정확히 3조각인지 확인. 아니면 거부
2. HMAC 을 재계산하고, 디코드한 서명이 **정확히 32바이트**인지 확인. 아니면 거부
3. `crypto.timingSafeEqual` 로 비교. 불일치면 거부
4. **여기서 처음** `JSON.parse`. 파싱 실패는 거부
5. `exp > now` 확인. 아니면 거부
6. `exp - iat <= 28800`(8시간) 확인. 아니면 거부 — 공격자가 만료를 늘린 토큰을 만들 수
   없더라도, 서버 버그로 긴 만료가 발급되는 것을 막는 상한이다
7. `pv` 가 현재 값과 일치하는지 확인(AUTH-8). 아니면 거부

순서가 중요하다. 서명 미검증 상태의 JSON 을 파싱하면 파서에 신뢰 없는 입력을 먹이게 된다.

> 검증: 유효한 토큰의 payload 를 한 글자 바꾼 값, 서명을 자른 값, `v1.` 접두어를 뺀 값,
> `exp` 를 미래로 늘린 값 네 가지가 모두 401/리다이렉트로 처리된다.

**AUTH-6 (필수) — 세션 쿠키 속성값은 다음으로 고정한다.**

| 속성 | 값 | 이유 |
| --- | --- | --- |
| 이름 | `__Host-admin_session` | `__Host-` 접두어는 브라우저가 `Secure` + `Path=/` + `Domain` 미지정을 강제한다. 하위 도메인에서 쿠키를 덮어쓰는 공격을 막는다 |
| `HttpOnly` | 있음 | JS 접근 차단. XSS 가 나도 쿠키 자체는 못 읽는다 |
| `Secure` | 있음 | HTTPS 로만 전송 |
| `SameSite` | `Strict` | 관리자 화면은 외부에서 링크로 들어올 일이 없다. `Lax` 는 최상위 GET 을 허용하므로 `Strict` 를 쓴다 |
| `Path` | `/` | `__Host-` 요구사항. 경로 제한은 실질적 보안 경계가 아니다(HttpOnly 라 JS가 못 읽는다) |
| `Domain` | 미지정 | `__Host-` 요구사항 |
| `Max-Age` | `28800` (8시간) | 절대 만료. 슬라이딩 갱신 없음 |

주의할 점 둘.

`Secure` 쿠키는 `http://localhost` 에서는 동작한다(브라우저가 localhost 를 보안
컨텍스트로 취급). 그러나 `http://192.168.x.x:3100` 같은 LAN IP 로 개발 서버에 접속하면
쿠키가 저장되지 않는다. 모바일 실기기 테스트가 필요하면 그때 별도로 다룬다. **개발 편의를
위해 `Secure` 를 끄는 분기를 만들지 마라.** 필요하면 `NODE_ENV !== 'production'` 조건에서
쿠키 이름의 `__Host-` 접두어만 떼는 것까지가 상한이고, 그 분기는 반드시 fail-closed 여야 한다.

`SameSite=Strict` 는 외부 사이트의 링크를 클릭해 `/admin` 에 들어오면 로그인 상태가
아닌 것처럼 보인다. 북마크나 주소창 직접 입력은 정상 동작한다. 관리자 화면에서는 허용되는
불편이다.

**AUTH-7 (필수) — 만료는 절대 8시간. 슬라이딩 갱신을 넣지 않는다.**

작업 중 로그아웃되는 불편이 있지만, 서버측 세션 저장소가 없는 구조에서는 짧은 만료가
유일한 실질적 취소 수단이다. 갱신을 넣으면 한 번 탈취된 토큰이 무한히 연장된다.

구현상 함정: Next.js 에서 쿠키 쓰기는 Server Action, Route Handler, 또는 `proxy.ts` 의
응답에서만 가능하다. Server Component 렌더 중에는 쓸 수 없다. 슬라이딩 갱신을 하려면
`proxy.ts` 에서 매 요청 쿠키를 재발급해야 하는데, proxy 는 CDN 에 배포될 수 있는 계층이라
그런 상태 조작을 두기에 적절하지 않다. 넣지 않는 편이 구조적으로도 맞다.

**AUTH-8 (필수) — 전체 세션 일괄 무효화 스위치를 만든다.**

payload 의 `pv` 는 다음 값으로 정한다.

```
pv = sha256( ADMIN_PASSWORD_HASH + "|" + (ADMIN_SESSION_EPOCH ?? "0") ).hex.slice(0, 16)
```

이렇게 하면 비밀번호를 교체하거나 `ADMIN_SESSION_EPOCH` 환경변수를 1 증가시키는 것만으로
**발급된 모든 세션이 즉시 무효**가 된다. 서버측 세션 저장소 없이 "모든 기기에서
로그아웃"을 얻는다. 비밀번호가 유출됐다고 의심되는 순간의 유일한 대응 수단이므로 필수다.

> 검증: 로그인 상태에서 `ADMIN_SESSION_EPOCH` 를 바꾸고 재기동하면 기존 쿠키로
> 관리자 접근이 거부된다.

### 1.4 로그인 시도 제한 — 서버리스에서 실제로 가능한 것

**솔직한 결론부터. 서버리스에서 신뢰할 수 있는 로그인 시도 제한은 공유 상태 없이 불가능하다.**

Vercel 함수는 요청마다 다른 인스턴스에서 실행될 수 있고, 콜드 스타트로 메모리가 초기화된다.
프로세스 메모리에 둔 카운터는 인스턴스 수만큼 병렬로 우회되고 시간이 지나면 사라진다.
JSON 파일에 카운터를 두는 것도 프로덕션에서는 파일시스템이 읽기 전용이라 불가능하다.

그래서 실제 방어선은 시도 제한이 아니라 **비밀번호 엔트로피**다. 순서를 바꿔서 적는다.

**AUTH-9 (필수) — 비밀번호는 사람이 만들지 않는다. 난수 20자 이상.**

`openssl rand -base64 24` 수준(약 128비트)의 값을 쓰고 비밀번호 관리자에 저장한다.
브랜드명·연도·전화번호가 섞인 문구는 금지다. 엔트로피가 100비트를 넘으면 온라인 대입은
시도 제한이 전혀 없어도 성립하지 않는다. **이것이 T1 에 대한 실질적 대응이고, 나머지는
보조 수단이다.** 이 요건은 코드가 아니라 운영 규칙이므로, 대표에게 명시적으로 전달하고
`docs/admin-architecture.md` 의 환경변수 안내에도 같은 내용을 넣어야 한다.

**AUTH-10 (필수) — 모든 로그인 응답에 고정 지연 하한을 둔다.**

성공·실패·환경변수 미설정 등 모든 경로에서 응답까지 최소 700ms 가 걸리게 한다. 시작
시각을 재고 부족한 만큼 대기한다. 효과가 둘이다. 한 커넥션당 시도 속도를 초당 1.4회로
묶는다. 그리고 scrypt 계산 유무에 따른 응답 시간 차이(= 해시가 설정되어 있는지 여부)를
가린다.

scrypt 자체의 계산 비용(N=16384 에서 약 100ms)도 시도당 비용으로 작용한다. 이건 부수 효과다.

**AUTH-11 (권장) — 인스턴스 메모리 카운터를 둔다. 단, 이것을 방어선이라고 부르지 않는다.**

모듈 스코프 `Map<ip, {count, firstAt}>` 으로 5분 내 10회 초과 시 추가 지연(예: 3초)을
준다. 단일 커넥션으로 반복하는 순진한 스크립트는 이걸로 걸린다. 병렬 요청이나 IP 교체에는
무력하다. **`proxy.ts` 에 두지 마라** — proxy 는 앱 런타임과 분리되어 실행될 수 있고
공식 문서가 공유 모듈·전역 의존을 금지한다. 로그인 Server Action 쪽에 둔다.

**AUTH-12 (필수) — 계정 잠금을 넣지 않는다.**

계정이 하나뿐이라 잠금은 곧 서비스 거부 취약점이다. 아무나 틀린 비밀번호를 10번 보내서
대표를 잠글 수 있다. 지연으로만 대응한다.

**AUTH-15 (권장) — Vercel WAF 의 rate limit 규칙을 `/admin/login` 경로에 설정한다.**

플랫폼 엣지에서의 제한이 유일하게 서버리스 우회에 강하다. **다만 Vercel 계정이 아직
없어서 지금은 설정도 검증도 불가능하다.** 새 계정으로 첫 배포한 직후 작업 항목으로 남긴다.

**AUTH-16 (나중) — Upstash Redis 또는 Vercel KV 로 분산 카운터를 구현한다.**

정확한 시도 제한을 원하면 이 방법뿐이다. 외부 서비스 계정이 하나 더 늘어나고, 그 계정도
신규 개설 정책의 대상이 된다. 지금 범위 밖이다. AUTH-9 를 지키면 급하지 않다.

### 1.5 로그아웃과 만료 처리

**AUTH-17 (필수) — 로그아웃은 Server Action 으로 처리하고, 쿠키를 동일 속성으로 삭제한다.**

쿠키 삭제는 발급 때와 **같은 이름·같은 Path** 로 `Max-Age=0` 을 내려야 한다. 이름이나
Path 가 다르면 브라우저가 다른 쿠키로 보고 기존 쿠키가 남는다. 삭제 후 `/admin/login`
으로 리다이렉트한다.

로그아웃 버튼은 `<form action={logout}>` 의 submit 이어야 한다. `<a href="/admin/logout">`
같은 GET 링크로 만들면 이미지 태그나 프리페치로 원치 않는 로그아웃이 유발될 수 있다.

서버측 세션 저장소가 없으므로 **로그아웃은 그 브라우저의 쿠키만 지운다.** 이미 탈취된
토큰은 만료(8시간)까지 유효하다. 전체 무효화가 필요하면 AUTH-8 을 쓴다. 이 한계를
`docs/admin-architecture.md` 에도 적어 두는 게 좋다.

**AUTH-18 (필수) — 만료 시 편집 중이던 입력을 잃지 않게 한다.**

콘텐츠 편집 중 8시간이 지나 액션이 401 을 받으면, 화면 전체를 로그인으로 날려버리면
작업물이 사라진다. 액션은 "세션이 만료되었습니다. 다시 로그인해 주세요"를 반환하고,
프론트는 현재 폼 상태를 유지한 채 로그인 안내를 표시한다. 선우 담당이다.

이건 UX 요건처럼 보이지만 보안 요건이다. 작업물을 잃는 경험이 반복되면 사람은 만료를
길게 늘리거나 인증을 우회하는 방향으로 압력을 만든다.

**AUTH-19 (권장) — 로그인 성공·실패·로그아웃 시각을 기록한다.**

개인정보 없이 `{ event, at, ip, ok }` 만 남긴다. 침해 사고가 났을 때 이 기록이 없으면
언제 뚫렸는지 판단할 수 없다. 저장 위치는 상담 데이터와 같은 어댑터를 쓴다.
프로덕션에서 파일 쓰기가 불가능한 문제는 8절과 동일하게 걸린다.

### 1.6 관리자 라우트 보호 — 놓치기 쉬운 우회 경로

**이 절이 이 문서에서 가장 중요하다.** Next.js 16 에서 인증을 `proxy.ts` 하나에 맡기면
반드시 구멍이 생긴다. 공식 문서가 명시적으로 경고하는 지점들을 포함해 정리한다.

**P1 (필수) — 파일은 `proxy.ts` 이고 함수명은 `proxy` 다. `middleware.ts` 와 공존시키지 않는다.**

Next.js 16 에서 `middleware` 파일 규약은 deprecated 되고 `proxy` 로 이름이 바뀌었다.
두 파일이 동시에 존재하는 상태를 만들지 마라. 어느 쪽이 우선인지에 의존하는 코드는
업그레이드에서 조용히 깨진다.

**P2 (필수) — matcher 는 `/admin` 과 `/admin/:path*` 를 모두 포함한다.**

`/admin/:path*` 만 쓰면 `/admin` **정확히 그 경로**가 빠진다. path-to-regexp 에서 `*` 는
"0개 이상"이지만 앞의 `/` 가 필요하다. 둘 다 나열해라.

> 검증: 로그아웃 상태에서 `/admin`, `/admin/`, `/admin/consults`, `/admin/content`
> 네 경로가 모두 로그인으로 리다이렉트된다.

**P3 (필수) — Server Action 은 별도 라우트가 아니다. 액션마다 자체 인증 확인을 한다.**

공식 문서가 명시한다. Server Function 은 라우팅 체인의 독립 라우트가 아니고, **그 함수를
사용하는 페이지 라우트로 가는 POST 요청**으로 처리된다. 여기서 두 가지가 따라온다.

첫째, proxy matcher 가 어떤 경로를 제외하면 그 경로의 Server Action 호출도 proxy 를
건너뛴다. 둘째이며 더 위험한 쪽 — **관리자용 액션을 공개 페이지 컴포넌트 트리에서
import 하면, 그 액션은 공개 라우트의 POST 로 호출 가능해지고 `/admin` matcher 는
아예 적용되지 않는다.**

그래서 두 요건이다.

- 모든 관리자 액션의 **첫 줄**이 `await requireAdmin()` 이다. 조건문 안이 아니라 첫 줄이다
- 관리자 액션이 정의된 파일은 `src/app/admin/**` 하위에서만 import 된다. 공개 섹션
  컴포넌트가 그 파일을 import 하는 일이 없다

> 검증: 관리자 액션 파일을 import 하는 파일 목록을 뽑았을 때 전부 `admin` 경로 하위다.
> 그리고 `requireAdmin` 호출이 없는 `'use server'` 함수가 관리자 액션 파일에 0개다.

**P4 (필수) — Route Handler(`/api/**`) 는 관례상 matcher 에서 제외된다. 핸들러 안에서 다시 확인한다.**

matcher 부정 패턴 예시들이 전부 `api` 를 제외하고 있어서 그대로 복사하면 API 경로가
무방비가 된다. 업로드를 Route Handler 로 만들 경우(U5 참조) 특히 위험하다. 핸들러
첫 줄에서 인증을 확인하고, 실패 시 본문 없이 401 을 반환한다.

**P5 (필수) — `images.localPatterns` 로 이미지 최적화 경로를 제한한다.**

`/_next/image?url=...` 는 이미지 최적화 엔드포인트다. 이 경로는 보통 matcher 에서
제외되고, 로컬 경로의 파일을 읽어서 서빙한다. 관리자만 봐야 할 이미지가 최적화 대상
경로에 있으면 인증 없이 꺼낼 수 있다.

`next.config.ts` 에 공개 자산 디렉터리만 허용한다.

```ts
images: {
  localPatterns: [{ pathname: '/uploads/**', search: '' }],
}
```

`search: ''` 를 생략하면 임의 쿼리스트링이 허용된다. 명시해라. 그리고 **관리자 전용
이미지는 애초에 만들지 않는다** — 업로드된 이미지는 전부 공개 페이지에 노출될 콘텐츠
이미지다. 관리자 전용 이미지 개념이 생기는 순간 이 설계는 다시 검토해야 한다.

**P6 (필수) — `public/` 는 인증을 통과하지 않는다. 개인정보를 절대 두지 않는다.**

`public/` 의 파일은 파일시스템 라우트에서 서빙되고, matcher 가 정적 경로를 제외하면
proxy 도 타지 않는다. URL 만 알면 누구나 받는다. 따라서

- 상담 신청 JSON 은 `public/` 아래에 **절대** 두지 않는다
- 어떤 데이터 파일도 `public/` 에 두지 않는다
- 업로드 이미지는 공개될 콘텐츠이므로 공개 서빙이 맞다. 다만 파일명이 추측 불가해야
  한다(U7)

> 검증: `public/` 하위에 `.json` 파일이 없다. 저장소 어댑터의 기본 경로가 `public` 을
> 포함하지 않는다.

**P7 (필수) — 레이아웃에서의 인증 확인은 보안 경계가 아니다.**

부분 렌더링 때문에 레이아웃은 라우트 이동 시 다시 렌더되지 않는다. `admin/layout.tsx`
에서만 세션을 확인하면 이후 이동에서 확인이 일어나지 않는다. 공식 문서가 이 패턴을
권장하지 않는다고 명시한다.

확인은 **각 페이지**와 **데이터 접근 계층**에서 한다. `requireAdmin()` 을 상담 데이터를
읽는 함수 안에 넣어서, 어디서 호출되든 확인이 따라가게 만드는 편이 가장 안전하다.
레이아웃 확인은 추가로 두는 것은 좋지만 그것에 의존하지 않는다.

**P8 (필수) — 관리자 페이지는 정적 프리렌더되지 않아야 한다.**

정적 프리렌더된 페이지는 빌드 시점 데이터가 정적 자산으로 존재한다. 라우트는 proxy 가
막아도 빌드 산출물에 박힌 데이터는 다른 문제다. 관리자 페이지는 쿠키를 읽으므로 자연히
동적이 되지만, 명시적으로 보장해라.

- `export const dynamic = 'force-static'` 을 관리자 라우트에 쓰지 않는다
- 관리자 라우트에 `generateStaticParams` 를 두지 않는다
- 필요하면 `await connection()` 으로 명시적으로 동적화한다

> 검증: `npx next build` 출력에서 `/admin/*` 항목이 정적(프리렌더)으로 표시되지 않는다.
> DEVNOTE 8절에 이 확인 결과를 기록한다.

**P9 (필수) — `skipProxyUrlNormalize` 와 `skipTrailingSlashRedirect` 를 켜지 않는다.**

URL 정규화를 끄면 `/admin`, `/admin/`, 인코딩 변형이 서로 다른 경로로 취급되어 matcher
우회 표면이 생긴다. `next.config.ts` 에 이 옵션이 등장하면 안 된다.

**P10 (필수) — 인증 proxy 의 matcher 에 프리페치 제외 조건을 쓰지 않는다.**

CSP 문서가 권장하는 `missing: [{ type:'header', key:'next-router-prefetch' }]` 패턴은
**CSP 헤더 부착용**이다. 이걸 인증 matcher 에 그대로 쓰면 프리페치 요청이 인증을
건너뛴다. 공식 문서도 인증 목적이면 모든 라우트에서 proxy 를 돌리라고 권한다.
CSP 와 인증의 matcher 를 같은 것으로 만들지 마라.

**P11 (필수) — proxy 안에서 저장소·파일시스템·모듈 전역 상태에 접근하지 않는다.**

proxy 는 앱 런타임과 분리되어 CDN 에 배포될 수 있다. 공식 문서가 공유 모듈·전역 의존을
하지 말라고 명시한다. proxy 가 하는 일은 **쿠키 서명 검증과 리다이렉트, 그리고 CSP 헤더
부착까지**다. 상담 데이터 조회, 시도 횟수 카운팅, 파기 작업을 여기 두지 않는다.

**P12 (필수) — proxy 의 확인은 낙관적 확인이고, 실제 차단은 페이지·액션·핸들러가 한다.**

proxy 는 세션 쿠키의 서명과 만료만 본다. 그걸로 리다이렉트를 결정하되, 그 뒤의 모든
데이터 접근 지점이 독립적으로 다시 확인한다. proxy 가 어떤 이유로든 실행되지 않는
경로가 생겨도 데이터는 새지 않아야 한다.

**P13 (권장) — `unauthorized()` / `forbidden()` 사용은 실험 플래그가 필요하다.**

`next/navigation` 의 `unauthorized()`, `forbidden()` 과 대응하는 `unauthorized.tsx`,
`forbidden.tsx` 를 쓰려면 `experimental.authInterrupts` 를 켜야 한다. 실험 기능에
인증 흐름을 의존시키지 말고, 지금은 `redirect('/admin/login')` 으로 처리한다.

## 2. 상담 신청 개인정보

### 2.1 수집 항목 최소화 검토

현재 폼은 이름, 연락처, 상담 희망 시간, 고민되는 점을 받는다. 각각을 판단한다.

| 항목 | 판단 | 근거 |
| --- | --- | --- |
| 이름 | **필수 유지** | 전화 상담에서 호칭이 필요하다. 다만 성만 받아도 목적은 달성된다(아래 참조) |
| 연락처 | **필수 유지** | 회신 수단. 이것 없이는 서비스가 성립하지 않는다 |
| 상담 희망 시간 | **선택으로 유지** | 통화 시도 횟수를 줄여 실제 효용이 있다. 없어도 서비스는 성립하므로 선택이어야 한다 |
| 고민되는 점 | **재검토 필요 — 가장 위험한 필드** | 아래 별도 설명 |
| 이메일 | **추가하지 않는다** | 회신 수단이 이미 있다. 수집 항목을 늘릴 이유가 없다 |
| 상담 트랙 (hidden) | **추가 필요** | 개인정보가 아니고, DEVNOTE 6절의 미구현 항목이다 |

**PII-1 (필수) — "고민되는 점" 자유 입력 필드는 민감정보 유입 경로다.**

대상이 성인·시니어·리더다. 커리어 전환, 은퇴 설계, 조직 갈등을 상담하러 오는 사람이
자유 입력란에 쓰는 내용은 건강 상태, 정신적 어려움, 가족 관계, 직장 내 분쟁이 되기 쉽다.
이 중 건강·정신질환 관련 정보는 개인정보보호법 제23조의 **민감정보**이고, 민감정보는
다른 개인정보와 **별도의 동의**를 받아야 처리할 수 있다.

현재 동의 문구는 "개인정보(이름·연락처)"만 언급한다. 즉 지금 이 필드에 들어오는 내용은
**동의 범위를 벗어난 수집**이 될 소지가 있다. **[법률 검토 필요]** — 자유 입력란에 정보
주체가 자발적으로 적은 민감정보의 처리 근거를 어떻게 보는지는 판단이 필요하다.

세 가지 선택지를 제시한다. 결정은 대표가 한다.

1. **필드 제거** — 가장 안전하다. 어떤 고민인지는 첫 통화에서 듣는다. 전환율 영향은
   얌얌이 판단할 문제다
2. **선택형으로 대체** — "관심 영역"을 라디오/체크박스(커리어 전환 / 은퇴 설계 / 조직·리더십
   / 기타)로 바꾼다. 서버에서 enum 화이트리스트로 검증되고, 민감정보가 들어올 여지가
   구조적으로 없다. **내 권장안이다**
3. **유지하되 방어** — 필드를 남기려면 아래 전부가 필수다
   - 라벨을 "선택"으로 명시
   - 플레이스홀더 또는 도움말에 "건강·질병 등 민감한 정보는 적지 말아 주세요. 자세한
     내용은 통화에서 말씀해 주세요"
   - 동의 문구와 처리방침의 수집 항목에 이 필드를 포함
   - 서버측 길이 상한 1000자
   - 관리자 목록에서 기본 미표시(상세 열람에서만)

**PII-2 (필수) — 상담 트랙 hidden 필드는 서버에서 화이트리스트로 검증한다.**

DEVNOTE 6절에 "대상별 CTA가 전부 `#consult` 로만 간다. 폼 전송 붙일 때 hidden 필드로
처리"라고 남아 있다. hidden 필드는 클라이언트가 임의 값을 넣을 수 있다. 허용값은
`adult | senior | leader | unknown` 뿐이고, 그 외는 `unknown` 으로 강제하거나 거부한다.
이 값을 그대로 화면에 렌더하면 XSS 벡터가 된다.

**PII-3 (필수) — 클라이언트 검증은 UX 용이다. 서버에서 전체를 다시 검증한다.**

현재 `ConsultForm.tsx` 의 검증은 브라우저 안에만 있다. `curl` 로 액션에 직접 POST 하면
전부 통과한다. 서버측 스키마 요건은 다음이다.

| 필드 | 규칙 |
| --- | --- |
| `name` | 문자열, trim 후 2~40자. 제어문자·개행 제거. 필수 |
| `phone` | 숫자만 남긴 뒤 10~11자리. 정규화된 값을 저장한다(하이픈 제거) |
| `preferredTime` | 문자열, 0~100자. 선택 |
| `message` | 문자열, 0~1000자. 선택 (PII-1 결정에 따라 제거 가능) |
| `track` | enum 화이트리스트. PII-2 |
| `agree` | `true` 여야 한다. 아니면 거부 |
| `honeypot` | 비어 있어야 한다. RATE-1 |
| `renderedAt` | 서명된 타임스탬프. RATE-2 |

`zod` 를 쓰면 편하지만 **현재 의존성에 없다.** 스키마 검증 라이브러리 도입은 데이브가
`docs/admin-architecture.md` 에서 판단할 사안이다. 어느 쪽이든 위 규칙이 서버에서
전부 적용되는 것이 요건이다. 직접 쓰는 검증 함수로도 충족된다.

`zod` 를 쓰는 경우 **에러 객체를 그대로 클라이언트에 반환하지 마라.** zod 의 issue 에는
일부 유형에서 입력값(`received`)이 포함된다. 필드명과 자체 메시지로만 매핑한다(LOG-3).

**PII-4 (권장) — 이름은 성만 받는 것을 검토한다.**

목적이 "전화할 때 호칭"이라면 "김"만 있어도 달성된다. 최소수집 원칙(제3조 제1항)에
가장 충실한 형태다. 다만 동명이 늘어나 식별이 어려워지는 실무 비용이 있다. 대표 판단
사항으로 남긴다. 지금은 전체 이름 유지가 현실적이다.

**PII-5 (필수) — 만 14세 미만 미수집을 명시한다.**

제22조의2 에 따라 만 14세 미만 아동의 개인정보는 법정대리인 동의가 필요하다. 이 서비스는
성인·시니어·리더 대상이며 아동 데이터를 받지 않는다. 생년월일을 수집하지 않으므로 나이를
검증할 방법이 없다. 따라서 **고지로 처리한다** — 폼 근처와 처리방침에 "만 14세 이상만
신청할 수 있습니다"를 명시한다. 나이 확인 절차를 만들려면 생년월일 수집이 필요해지는데,
그건 최소수집에 역행한다. 고지가 합리적 균형이다. **[법률 검토 필요]** — 고지만으로
충분한지 확인이 필요하다.

### 2.2 보관 위치 · 접근 주체

**PII-6 (필수) — 상담 데이터 파일은 저장소 밖·라우트 밖에 두고 git 에서 제외한다.**

`public/` 금지는 P6 에 있다. 추가로,

- `src/app/` 하위에 두지 않는다 (라우트 해석 대상 디렉터리)
- 저장 경로를 `.gitignore` 에 추가한다. **이름과 전화번호가 담긴 JSON 이 git 에 커밋되면
  히스토리에서 지우기 어렵고, 이 저장소는 곧 새 GitHub 계정으로 push 될 예정이다.**
  한 번 push 되면 되돌릴 수 없다
- 파일 권한은 POSIX 환경에서 `0600`. Windows 로컬에서는 의미가 없지만 배포 환경 기준으로
  명시한다

`.gitignore` 에 들어갈 항목(경로는 데이브의 결정을 따른다).

```
/data/
/uploads/
```

> 검증: `git check-ignore -v data/consults.json` 가 규칙에 매칭된다.
> `git log --all -- data/` 가 비어 있다.

**PII-7 (필수) — 접근 주체는 단일 관리자뿐이다. 다른 읽기 경로를 만들지 않는다.**

상담 데이터를 읽는 함수는 하나여야 하고, 그 함수가 `requireAdmin()` 을 호출한다.
공개 페이지에서 이 데이터를 읽는 코드가 생기지 않게 한다. 통계·카운터 같은 것도
"이번 달 상담 신청 12건" 형태로 공개 페이지에 노출하고 싶어지는 순간 경로가 하나 늘어난다.
지금은 만들지 않는다.

**PII-8 (권장) — `experimental.taint` 를 켜고 연락처 값을 taint 한다.**

`taintUniqueValue` 로 전화번호를 표시해 두면 Client Component 로 실수 전달될 때 React 가
에러를 던진다. 실험 기능이고 유일한 방어 수단으로 삼아서는 안 되지만, 방어적 장치로는
값이 있다. 켜면 React experimental 채널이 활성화된다는 점은 감안해야 한다. 프레임워크
채널이 바뀌는 영향이 있으니 데이브·선우와 합의한 뒤 켠다.

### 2.3 보유기간과 파기 — 약속한 6개월을 실제로 이행하는 방법

**현재 동의 문구는 구조적 결함이 있다.** "상담 종료 후 6개월 이내 파기"라고 약속했는데,

1. 시스템에 "상담 종료" 시점을 기록하는 곳이 없다
2. 신청만 하고 상담이 진행되지 않은 사람은 **상담 종료 시점이 영원히 오지 않는다.**
   문구를 그대로 해석하면 파기 시점이 정의되지 않아 무기한 보관이 된다

무기한 보관은 제21조(보유기간 경과·목적 달성 시 지체 없이 파기) 위반이다. 문구를 지키려면
결정론적 규칙이 필요하다.

**PII-9 (필수) — 레코드에 보유기간 계산용 필드를 둔다.**

| 필드 | 의미 |
| --- | --- |
| `id` | 무작위 식별자. 순번을 쓰지 않는다(열거 가능해진다) |
| `receivedAt` | 접수 시각 (서버 시각, ISO 8601) |
| `contactedAt` | 첫 회신 시각. null 허용 |
| `closedAt` | 상담 종료 시각. **관리자가 명시적으로 기록한다.** null 허용 |
| `purgeAt` | 파기 예정 시각. 아래 규칙으로 계산해 저장한다 |

**PII-10 (필수) — 파기 시점 규칙을 다음으로 확정한다.**

```
상담이 종료된 경우      : purgeAt = closedAt + 180일
상담이 진행되지 않은 경우 : purgeAt = receivedAt + 180일   (미연락 종결로 간주)
절대 상한               : receivedAt + 365일. closedAt 유무와 무관하게 이 시점에 파기
```

절대 상한이 필요한 이유는 관리자가 `closedAt` 을 계속 비워두거나 늦게 기록해서 보관이
무한정 늘어나는 것을 막기 위해서다. 최대 보관기간이 365일로 고정된다.

**이 규칙은 현재 동의 문구보다 넓다.** 문구는 "상담 종료 후 6개월"만 말하고 미상담 건과
절대 상한을 다루지 않는다. 따라서 **동의 문구와 처리방침을 이 규칙에 맞춰 갱신해야 한다.**
문구 작성은 로보 담당이고, 최종 표현은 **[법률 검토 필요]** 다. 갱신 없이 이 규칙만
구현하면 공개된 약속과 실제 처리가 어긋난다.

**PII-11 (필수) — 파기 실행: 지연 파기(lazy purge)를 기본으로 한다.**

서버리스에는 상시 크론이 없다. 대신 다음을 조합한다.

1. **지연 파기 (필수)** — 상담 데이터를 읽거나 쓰는 **모든** 경로에서, 본 작업 전에
   `purgeAt <= now` 인 레코드를 먼저 삭제한다. 신규 접수 시에도 실행되므로 폼이
   살아 있는 한 파기도 돌아간다. 추가 인프라가 0이다
2. **`after()` 로 응답 후 실행 (권장)** — `next/server` 의 `after()` 를 쓰면 응답을
   보낸 뒤에 파기를 돌릴 수 있어 사용자 응답 시간에 영향을 주지 않는다
3. **Vercel Cron (권장, 계정 개설 후)** — `vercel.json` 의 `crons` 로 하루 1회 파기
   엔드포인트를 호출한다. 아무도 사이트를 방문하지 않는 기간에도 파기가 보장된다.
   엔드포인트는 `CRON_SECRET` 으로 보호한다(Vercel 이 `Authorization: Bearer` 로 보낸다).
   **계정이 없어 지금 검증 불가**
4. **관리자 수동 파기 (필수)** — 레코드별 삭제 버튼. 그리고 목록에서 `purgeAt` 이 지난
   레코드에 "파기 예정" 표시. 자동 파기가 어떤 이유로 돌지 않아도 사람이 개입할 수 있다

지연 파기만으로는 "아무도 방문하지 않으면 파기되지 않는다"는 구멍이 남는다. 솔직하게
적는다. 크론이 붙기 전까지는 이 구멍이 존재하며, 실제 트래픽이 있는 사이트에서는
현실적으로 매일 실행된다.

**PII-12 (필수) — 파기 방법은 복원 불가능한 삭제여야 한다.**

시행령 제16조 제1항은 전자적 파일 형태의 개인정보를 "복원이 불가능한 방법으로 영구 삭제"
하도록 정한다. JSON 파일에서 레코드를 제거할 때 다음을 지킨다.

- 삭제 후 파일을 원자적으로 교체하되(임시 파일 → rename), **임시 파일을 남기지 않는다**
- 삭제된 레코드가 `.bak`, `.old`, 로그, git 에 남지 않는다
- "삭제 플래그만 세우고 데이터는 남기는" 소프트 삭제를 쓰지 않는다. 그건 파기가 아니다
- Supabase 로 옮긴 뒤에는 백업 스냅샷에 남는 문제가 새로 생긴다. 그때 재검토한다

**PII-13 (필수) — 파기 기록을 개인정보 없이 남긴다.**

`{ recordId, purgedAt, reason: 'retention' | 'manual' }` 만 남긴다. 이름·연락처를 파기
기록에 남기면 파기가 아니게 된다. 표준 개인정보 보호지침은 파기 관리대장 작성을 권하는데,
그 대장에 개인정보를 적으면 안 된다는 점이 실무에서 자주 틀린다.

### 2.4 관리자 조회 화면에서의 취급

**PII-14 (필수) — 목록에서는 연락처를 마스킹한다. 전체 노출은 명시적 행동으로 한다.**

목록은 한 화면에 여러 사람의 연락처를 동시에 띄운다. 화면 공유, 어깨 넘어 보기,
스크린샷 한 장으로 여러 건이 함께 유출된다. 목록의 기본 상태는 마스킹이다.

- 이름: 첫 글자 + 나머지 `*` (`김*수`)
- 연락처: 가운데 4자리 `*` (`010-****-5678`)
- "고민되는 점": 목록에 표시하지 않는다

전체 값이 필요한 건 통화할 때다. 행별 "연락처 보기" 또는 상세 화면에서 전체를 노출하고,
그 열람을 기록한다(PII-16). 이렇게 하면 "필요할 때만 본다"가 구조로 강제된다.

수진의 `docs/admin-ui.md` 와 충돌할 수 있는 지점이다. 마스킹은 협상 대상이 아니지만
마스킹을 푸는 인터랙션의 형태(툴팁·모달·상세 페이지)는 수진이 정하면 된다.

**PII-15 (필수) — 개인정보를 URL 에 넣지 않는다.**

검색·필터를 만들 때 `?phone=010...` 이나 `?q=김` 같은 쿼리스트링을 쓰지 마라. URL 은
서버 액세스 로그, 브라우저 히스토리, `Referer` 헤더에 남는다. Vercel 함수 로그에도
경로가 기록된다. 검색은 Server Action 또는 POST 로 처리하고, 상세 페이지의 경로 파라미터는
무작위 `id` 만 쓴다.

**PII-16 (권장) — 개인정보 열람·삭제 기록을 남긴다.**

개인정보의 안전성 확보조치 기준(고시) 제8조는 개인정보취급자의 개인정보처리시스템 접속기록을
1년 이상 보관·관리하도록 정한다. **[법률 검토 필요]** — 이 고시의 적용 대상과 정확한
보관기간이 이 규모의 처리자에게 어떻게 적용되는지 확인이 필요하다.

기록 항목은 계정(단일 admin), 일시, 접속지 IP, 수행 업무(목록조회 / 상세열람 / 삭제 /
내보내기), 대상 레코드 id 다. **레코드의 내용은 남기지 않는다.**

접속기록에 IP 를 남기는 것 자체가 개인정보 수집이지만, 법적 의무 이행을 위한 처리이므로
처리방침에 기재하면 된다. 기재를 빼먹지 마라.

**PII-17 (필수) — 관리자 페이지 응답을 캐시하지 않는다.**

상담 목록이 CDN이나 브라우저 캐시에 남으면 로그아웃 후에도 뒤로가기로 보인다.
`/admin/:path*` 에 `Cache-Control: no-store, must-revalidate` 를 설정한다(HDR-9).
쿠키를 읽는 동적 라우트는 Next.js 가 기본적으로 캐시하지 않지만, 명시하는 편이 안전하다.

### 2.5 로그·에러 응답에서 개인정보를 막는 규칙

**Vercel 함수 로그는 플랫폼에 보관되고 대시보드 접근 권한이 있는 사람에게 보인다.**
즉 로그에 이름과 전화번호를 찍는 것은 사실상 개인정보를 제3자 인프라로 내보내는 행위다.
"디버깅용 임시 로그"가 프로덕션에 남는 것이 가장 흔한 유출 경로다.

**LOG-1 (필수) — 다음 패턴을 금지한다.**

```
console.log(formData)              // FormData 전체
console.log(record)                // 레코드 전체
console.log(JSON.stringify(record))
console.error(error)               // 에러 객체 전체 (message 에 입력값이 섞일 수 있다)
console.log('phone:', phone)
```

**LOG-2 (필수) — 허용되는 로그 형태를 정한다.**

```
console.info('consult.created', { id })
console.warn('consult.rejected', { reason: 'schema' })
console.error('consult.store_failed', { id, errorId })
```

레코드를 로그에 넘겨야 할 일이 생기면 `logSafe(record)` 를 거친다. 이 함수는
`{ id, receivedAt, track, hasMessage: boolean }` 만 반환한다. 화이트리스트 방식이어야
한다. 필드를 지우는 블랙리스트 방식은 새 필드가 추가될 때 조용히 새게 된다.

**LOG-3 (필수) — 클라이언트로 돌아가는 값에 입력값을 담지 않는다.**

- 검증 실패 응답은 `{ field, message }` 형태의 자체 메시지다. 입력값을 되돌려주지 않는다
- zod 등의 issue 객체를 그대로 반환하지 않는다. 일부 issue 유형은 `received` 에 입력값을
  포함한다
- 내부 에러는 `{ ok: false, code: 'INTERNAL', errorId }` 만 반환한다. `errorId` 는 난수다.
  스택, 파일 경로, 저장소 경로, SQL, 예외 메시지를 클라이언트로 보내지 않는다
- **로그인 실패 시 입력한 비밀번호를 폼 `value` 로 되돌려 채우지 않는다.** 브라우저
  히스토리와 RSC 페이로드에 남는다

**LOG-4 (필수) — 상담 접수 성공 화면에 입력값을 다시 보여주지 않는다.**

현재 완료 화면은 "상담 신청이 접수되었습니다"만 표시한다. 좋다. 여기에 "010-1234-5678 로
연락드립니다" 같은 확인 문구를 추가하고 싶어질 수 있는데, 그 화면이 캐시되거나 스크린샷으로
남는다. 지금 형태를 유지한다.

**LOG-5 (권장) — 개발 서버 로그도 같은 규칙을 적용한다.**

로컬에서 찍은 로그가 화면 공유·스크린샷·터미널 파일로 나간다. `NODE_ENV` 로 분기해서
개발에서만 PII 를 찍는 코드를 만들지 마라. 그 분기는 언젠가 프로덕션에서 켜진다.

### 2.6 다운로드 / 내보내기

**PII-18 (나중) — CSV·엑셀 내보내기를 지금 만들지 않는다.**

이유가 명확하다. 내보내기는 **클릭 한 번으로 전체 개인정보를 암호화되지 않은 파일로
대표의 노트북에 복제**한다. 그 사본은

- 6개월 자동 파기 메커니즘의 적용을 받지 않는다. 약속한 파기가 그 순간 깨진다
- 이메일 첨부, 클라우드 동기화, 공유 폴더로 재확산된다
- 노트북 분실 시 유출 규모가 전체 데이터가 된다

지금 이 기능의 실질적 필요가 있는지도 불분명하다. 상담 건수가 적으면 화면에서 보고
전화하면 된다.

**나중에 만들 경우의 조건** (전부 충족해야 한다).

- 내보내기 직전 비밀번호 재입력(re-authentication)
- 기간·상태 필터 필수. "전체" 옵션 없음. 최대 행 수 상한
- 파일명에 개인정보를 넣지 않는다 (`consults-2026-09.csv`, 이름·전화번호 금지)
- 내보내기 실행을 접속기록에 남긴다 (PII-16)
- 화면에 "내보낸 파일은 자동 파기 대상이 아닙니다. 사용 후 직접 삭제하세요" 경고
- 처리방침의 보유기간 서술과 모순되지 않는지 재검토

### 2.7 알림 연동에 대한 사전 경고

**PII-19 (나중) — 신규 접수 알림(이메일·카카오·슬랙)을 붙이면 개인정보가 제3자로 나간다.**

DEVNOTE 6절에 "DB·알림 미연결"로 되어 있어 이번 범위는 아니지만, 붙이는 순간 다음이
발생한다. 메일/메시징 서비스는 **처리위탁**(제26조) 또는 **제3자 제공**(제17조)에 해당하고,
처리방침에 수탁자와 위탁 업무를 기재해야 한다. 서비스가 해외라면 국외이전(제28조의8)
문제가 추가된다. 알림 본문에 이름·연락처를 넣으면 그 내용이 메일 서버에 장기 보관된다.

**권장: 알림 본문에 개인정보를 넣지 않는다.** "새 상담 신청 1건이 접수되었습니다.
관리자 페이지에서 확인하세요"만 보낸다. 이렇게 하면 위탁 범위가 크게 줄어든다.
붙이기 전에 나에게 다시 검토를 요청해라.

## 3. 개인정보처리방침 페이지

### 3.1 게시 의무

**PRIV-1 (필수) — 처리방침을 정하고 공개한다.**

제30조 제1항은 개인정보처리자가 처리방침을 정하도록, 제2항은 정보주체가 쉽게 확인할 수
있도록 공개하도록 정한다. 시행령은 인터넷 홈페이지에 지속적으로 게재하되 첫 화면 또는
첫 화면과 연결되는 화면에 두도록 한다. 현재 이 사이트에는 페이지가 **없다.**
처리방침 미공개는 과태료 부과 대상이다. **[법률 검토 필요]** — 정확한 과태료 조항과
금액은 확인이 필요하다.

요건은 다음이다.

- 라우트: `/privacy` (경로명은 팀 합의로 정한다)
- 정적 렌더링, 검색엔진 색인 허용, `sitemap.ts` 에 포함
- **푸터에서 링크한다** — 원페이지 랜딩이므로 푸터가 "첫 화면과 연결되는 화면"에 해당한다
- **상담 폼 동의 문구 옆에서도 링크한다** — 동의하는 순간 내용을 확인할 수 있어야 한다
- 인증 없이 접근 가능. 처리방침을 관리자 뒤에 두는 실수를 하지 않는다

**PRIV-2 (필수) — 시행일자를 표시하고, 변경 시 이전 버전을 확인할 수 있게 한다.**

처리방침은 변경 이력 관리가 필요하다. 최소한 "시행일: YYYY-MM-DD"를 표시한다.
변경 시 변경 사항과 시행일을 함께 알리는 것이 원칙이다. 지금은 첫 버전이므로 시행일
표기까지가 필수다.

### 3.3 대표가 실제 값을 제공해야 하는 항목

**PRIV-3 (필수) — 아래 값을 대표에게서 받는다. 어떤 값도 지어내지 않는다.**

`src/lib/site.ts` 는 현재 전부 플레이스홀더다. `bizNo: "000-00-00000"`,
`email: "hello@example.com"`, `phone: "070-0000-0000"`, `owner: "○○○"`,
`addressLine: "3F, 00, ○○-ro, ○○-gu, Seoul"`. **이 값들이 그대로 처리방침에 실리면
공개된 법정 고지사항이 허위가 된다.** 처리방침은 마케팅 카피와 성격이 다르다.

| 항목 | 상태 | 비고 |
| --- | --- | --- |
| 상호(사업자명) | **미확정** | `SITE.company` 플레이스홀더 |
| 대표자 성명 | **미확정** | `SITE.owner` = `○○○` |
| 사업자등록번호 | **미확정** | `SITE.bizNo` = `000-00-00000` |
| 사업장 주소 | **미확정** | `SITE.addressLine` 플레이스홀더 |
| 대표 전화번호 | **미확정** | `SITE.phone` = `070-0000-0000` |
| 대표 이메일 | **미확정** | `SITE.email` = `hello@example.com` |
| 개인정보 보호책임자 성명 | **미확정** | 아래 참조 |
| 보호책임자 직책·부서·연락처 | **미확정** | 1인 사업자면 대표 본인 정보 |
| 처리방침 시행일자 | **미확정** | 게시 확정일 |
| 호스팅 등 수탁자 목록 | **미확정** | 배포 확정 후 (3.4) |
| 통신판매업 신고번호 | **해당 여부 미확정** | 유료 프로그램 판매 형태에 따라 달라진다. **[법률 검토 필요]** |

개인정보 보호책임자는 제31조에 따라 지정해야 한다. 시행령에 따르면 별도로 지정하지
않은 경우 사업주 또는 대표자가 보호책임자가 된다. 1인 운영이라면 대표가 겸하는 것으로
정리하면 되지만, **처리방침에는 이름과 연락처를 실제로 적어야 한다.** 이름 없이
"개인정보 보호책임자"만 적는 것은 요건 미충족이다. **[법률 검토 필요]**

**PRIV-4 (필수) — 값이 미확정인 상태로 처리방침을 게시하지 않는다.**

선택지가 둘이다. (a) 대표에게서 값을 받아 채운 뒤 게시하고 상담 폼 전송을 활성화한다.
(b) 값을 받기 전이면 **상담 폼 전송을 활성화하지 않는다.** 개인정보를 수집하면서 처리방침이
없거나 허위인 상태가 최악이다. 8절의 배포 차단 조건에 넣었다.

### 3.4 처리위탁 · 국외이전

**PRIV-5 (필수) — 호스팅 사업자를 수탁자로 기재한다.**

Vercel 에 배포하면 개인정보가 담긴 JSON(또는 이후 Supabase 데이터)과 함수 로그가 Vercel
인프라에 저장·처리된다. 이는 처리위탁에 해당하며, 처리방침에 수탁자명과 위탁 업무 내용을
기재해야 한다(제30조①4, 제26조).

**PRIV-6 (필수) — 국외이전 여부를 확인하고 기재한다.**

Vercel 과 Supabase 는 리전 선택에 따라 데이터가 국외(대체로 미국)에 저장된다.
제28조의8 은 국외이전에 별도 동의 또는 법정 예외 사유를 요구하고, 이전받는 자·국가·
이전 항목·이전 방법·보유기간·거부 방법 등을 알리도록 정한다.

실무적으로 취할 수 있는 조치가 둘이다.

1. **리전을 한국(또는 가까운 리전)으로 선택한다.** Vercel 은 함수 리전을,
   Supabase 는 프로젝트 리전을 선택할 수 있다. 국외이전 자체를 줄이는 것이 가장 깔끔하다.
   **새 계정 개설 시 리전을 반드시 확인하고 선택하도록 대표에게 전달해야 한다.**
   기본값으로 만들면 미국 리전이 될 가능성이 높다
2. 국외이전이 발생하면 처리방침에 필요 항목을 기재하고, 동의가 필요한지 판단한다

**[법률 검토 필요]** — 계약 이행을 위한 위탁으로서 처리방침 공개로 갈음할 수 있는
경우인지, 별도 동의가 필요한지는 법적 판단이 필요하다. 이건 내가 결론 내릴 사안이 아니다.

이 항목은 **계정 개설 순서에 영향을 준다.** 리전을 잘못 고르고 배포한 뒤 옮기는 것은
데이터 이전 작업이 된다. 계정 개설 시점에 결정해야 한다.

### 3.5 쿠키 기재

**PRIV-7 (필수) — 사용하는 쿠키를 정확히 기재한다.**

현재 계획상 쿠키는 관리자 세션 쿠키 하나다. 이것은 방문자(정보주체)에게 설정되지 않고
관리자에게만 설정된다. 기재는 하되 과장하지 않는다.

분석 도구(GA 등)를 도입하면 상황이 완전히 달라진다. 자동 수집 장치 기재, 거부 방법 안내,
그리고 도구 제공자가 수탁자로 추가된다. DEVNOTE 에 "분석 도구 도입 검토"가 얌얌 담당으로
있으니, **도입 전에 나에게 검토를 요청해라.**

### 3.6 현재 동의 문구와의 정합성 점검

현재 `ConsultForm.tsx` 의 문구는 이렇다.

> 상담 진행을 위한 개인정보(이름·연락처) 수집·이용에 동의합니다.
> 상담 종료 후 6개월 이내 파기됩니다.

점검 결과 **불일치 5건**을 발견했다. 전부 수정이 필요하다.

**CONS-1 (필수) — 수집 항목이 문구와 실제가 다르다.**

문구는 "이름·연락처"만 말하지만 폼은 희망시간과 고민되는 점도 받는다. 트랙 hidden 필드가
추가되면 하나 더 늘어난다. 동의 범위를 벗어난 항목을 수집하는 상태다. PII-1 결정에 따라
항목을 확정하고 문구를 맞춘다.

**CONS-2 (필수) — 파기 시점이 미상담 건을 다루지 않는다.**

2.3 에서 설명했다. PII-10 규칙에 맞춰 문구를 갱신한다.

**CONS-3 (필수) — 동의 거부 권리와 거부 시 불이익 고지가 없다.**

제15조·제22조는 동의를 받을 때 ① 수집·이용 목적 ② 수집 항목 ③ 보유·이용 기간
④ 동의 거부 권리 및 거부 시 불이익 내용을 알리도록 정한다. 현재 문구는 ④가 없다.
④는 관례적 문구가 아니라 법정 고지사항이다. **[법률 검토 필요]** — 정확한 표현 확인 필요.

**CONS-4 (필수) — 필수 동의와 선택 동의가 분리되어 있지 않다.**

제22조는 필수·선택 동의를 구분해 받도록 하고, 선택 동의를 거부해도 서비스 제공을 거부할
수 없도록 정한다. 지금은 체크박스 하나에 전부 묶여 있다. 정리 방향은 이렇다.

- **필수 동의**: 이름·연락처 (이것 없이는 상담 회신이 불가능하므로 필수가 정당하다)
- **선택 항목**: 희망시간, 관심영역/고민 — 입력 자체를 선택으로 두면 별도 동의 체크박스
  없이 "입력하지 않아도 됩니다"로 처리 가능한지가 판단 대상이다. **[법률 검토 필요]**

체크박스를 둘로 늘리면 전환율에 영향이 있다. 얌얌·로보와 함께 문구를 다듬어야 한다.
다만 **분리 자체는 협상 대상이 아니다.**

**CONS-5 (필수) — 처리방침 링크가 없다.**

동의 체크박스 옆에 `/privacy` 링크가 있어야 한다. 동의하는 시점에 전문을 확인할 수 있어야
한다는 취지다. 링크는 새 창(`target="_blank" rel="noopener noreferrer"`)으로 열어서
입력 중인 폼 내용이 사라지지 않게 한다. `rel="noopener"` 를 빼먹지 마라.

**CONS-6 (필수) — 문구 변경 후 처리방침과 다시 대조한다.**

동의 문구와 처리방침의 수집 항목·보유기간·목적이 **글자 단위로 일치**해야 한다.
둘 중 하나만 고치는 상황이 반복되면 반드시 어긋난다. 로보가 문구를 확정한 뒤 내가
대조 점검을 한 번 더 한다.

## 4. 파일 업로드 보안

관리자만 쓰는 기능이지만, 인증이 뚫렸을 때 파일 업로드는 "콘텐츠 훼손"에서 "서버 침해"로
피해 등급을 올린다. 그리고 업로드된 파일은 공개 URL 로 서빙되므로 방문자에게도 영향을 준다.

### 4.1 프로덕션 동작 가능성 — 먼저 확인할 것

**UP-0 (필수) — Vercel 런타임에서는 파일 업로드가 동작하지 않는다.**

서버리스 함수의 파일시스템은 읽기 전용이다. `public/` 에 쓸 수 없고, `/tmp` 만 쓸 수 있는데
`/tmp` 는 인스턴스별이고 휘발성이다. 즉 업로드해도 다음 요청에서 사라지거나 다른
인스턴스에서 보이지 않는다.

이건 보안 문제가 아니라 기능 성립 문제지만, **보안 관점에서 더 나쁜 시나리오가 있다.**
업로드가 실패했는데 UI 가 성공으로 표시되고, 대표가 "저장됐다"고 믿는 상태. 또는
`/tmp` 에 쓰고 그 경로를 그대로 서빙하려 시도하면서 경로 처리 코드가 복잡해지는 것.

따라서 요건은 이렇다.

- 로컬 개발에서는 파일시스템 어댑터로 동작한다
- **프로덕션 빌드에서 업로드 기능은 명시적으로 비활성화**하고, 관리자 UI 에
  "이미지 업로드는 저장소 연동 후 사용할 수 있습니다"를 표시한다. 조용히 실패시키지 않는다
- 또는 blob 스토리지(Vercel Blob, Supabase Storage)를 붙일 때까지 배포를 보류한다
- 어느 쪽이든 **"업로드가 성공한 것처럼 보이는" 상태를 만들지 않는다**

저장소 어댑터가 교체 가능하게 설계되어 있으므로(대표 결정사항), 이미지 저장도 같은
방식으로 어댑터 뒤에 둔다. 데이브의 `docs/admin-architecture.md` 와 맞춰라.

### 4.2 허용 형식과 크기

**UP-1 (필수) — 허용 형식은 JPEG, PNG, WebP 셋뿐이다.**

| 형식 | MIME | 확장자 | 판단 |
| --- | --- | --- | --- |
| JPEG | `image/jpeg` | `.jpg` | 허용 |
| PNG | `image/png` | `.png` | 허용 |
| WebP | `image/webp` | `.webp` | 허용 |
| AVIF | `image/avif` | `.avif` | 나중. 검증 로직이 복잡하고 지금 필요가 없다 |
| GIF | `image/gif` | — | 제외. 콘텐츠 이미지에 필요 없다 |
| SVG | `image/svg+xml` | — | **거부.** UP-3 |
| 그 외 | — | — | 거부 |

확장자는 **탐지된 형식에서 역산**한다. 클라이언트가 보낸 확장자나 `Content-Type` 을
신뢰하지 않는다.

**UP-2 (필수) — 크기 상한 5MB. 그리고 잘린 업로드를 반드시 검출한다.**

이게 이 절에서 가장 놓치기 쉬운 지점이다.

`proxyClientMaxBodySize` 는 기본 10MB 이고, **본문이 이 값을 넘으면 요청이 실패하지 않는다.**
공식 문서 그대로 — 앞부분만 버퍼링되고 경고 로그를 남긴 뒤 **부분 본문으로 정상 처리가
계속된다.** 그러면 잘린 이미지가 저장되는데, 앞부분은 온전하므로 **매직 바이트 검증은
통과한다.** 조용한 데이터 손상이다.

요건은 셋이다.

- 업로드 상한을 5MB 로 정하고 서버에서 강제한다
- `next.config.ts` 에 `experimental.proxyClientMaxBodySize` 를 명시적으로 설정한다.
  업로드 상한보다 충분히 크게(예: `'8mb'`) 두어 잘림이 애초에 발생하지 않게 한다
- **수신한 바이트 길이가 온전한 파일인지 검증한다.** 형식별 종료 구조를 확인한다
  (JPEG 는 `FFD9` 로 끝난다, PNG 는 `IEND` 청크가 있다). 또는 디코더로 전체를 파싱해
  성공하는지 본다(UP-9). 앞부분만 보는 검증은 불충분하다

**UP-3 (필수) — SVG 업로드를 거부한다.**

판단과 근거를 명확히 남긴다. **거부한다.**

SVG 는 이미지가 아니라 XML 문서다. `<script>`, 이벤트 핸들러 속성(`onload`),
`<foreignObject>` 안의 HTML, 외부 리소스 참조를 담을 수 있다. 이 파일이 사이트와
**같은 오리진**에서 서빙되고 브라우저가 직접 열면, 그 스크립트는 사이트 오리진의 권한으로
실행된다. 즉 저장형 XSS 이고, 관리자 세션 쿠키가 `HttpOnly` 라 직접 읽히지 않아도
관리자 권한으로 요청을 대신 보내는 것(콘텐츠 변조, 상담 데이터 조회)은 가능하다.

SVG 를 안전하게 만드는 방법이 없지는 않다. 파서로 허용 태그·속성 화이트리스트를 적용하는
것(DOMPurify 등)인데, 서버에서 돌리려면 `jsdom` 급 의존성이 필요하고, 우회 사례가
반복적으로 나오는 영역이다. Next.js 자체도 `next/image` 에서 SVG 를 다룰 때
`dangerouslyAllowSVG` 라는 이름을 쓰면서 `contentDispositionType: 'attachment'` 와
`contentSecurityPolicy: "default-src 'self'; script-src 'none'; sandbox;"` 를 함께 설정할
것을 강하게 권고한다. 프레임워크가 옵션 이름에 `dangerously` 를 붙인 이유가 있다.

**얻는 것과 잃는 것을 비교하면 답이 분명하다.** 얻는 것은 "로고를 관리자에서 교체하는
편의"다. 잃을 수 있는 것은 사이트 전체와 상담 데이터다. 로고·아이콘 같은 벡터 자산은
빈도가 낮으므로 **저장소에 자산으로 커밋하고 코드 리뷰를 거치는 경로**로 처리한다.
업로드 통로를 열지 않는다.

**UP-4 (필수) — `dangerouslyAllowSVG` 를 켜지 않는다.**

`next.config.ts` 에 이 옵션이 등장하면 안 된다. 어떤 이유로든 켜게 되면
`contentDispositionType: 'attachment'` 와 `contentSecurityPolicy` 를 반드시 함께 설정해야
하고, 그 전에 나에게 검토를 요청해라.

### 4.3 실제 파일 내용 검증

**UP-5 (필수) — 확장자와 `Content-Type` 을 신뢰하지 않는다. 매직 바이트를 확인한다.**

둘 다 클라이언트가 정하는 값이다. `payload.php` 를 `photo.jpg` 로 바꿔 보내는 것은
개발자 도구 없이도 가능하다.

| 형식 | 확인 위치와 값 |
| --- | --- |
| JPEG | 0번지 `FF D8 FF` |
| PNG | 0번지 `89 50 4E 47 0D 0A 1A 0A` (8바이트 전부) |
| WebP | 0번지 `52 49 46 46`(`RIFF`) **그리고** 8번지 `57 45 42 50`(`WEBP`) |

WebP 는 `RIFF` 만 확인하면 안 된다. WAV 등 다른 RIFF 컨테이너와 구분되지 않는다.
8번지의 `WEBP` 를 함께 봐야 한다.

**UP-6 (필수) — 픽셀 크기 상한을 검증한다.**

바이트 크기가 작아도 픽셀이 거대한 이미지는 디코딩 시 메모리를 폭발시킨다(디컴프레션 폭탄).
헤더에서 폭·높이를 읽어 **각 변 8000px 이하, 총 4천만 픽셀 이하**를 확인한다. 헤더 파싱이
실패하면 거부한다. 이 검증은 **디코딩 전에** 해야 의미가 있다.

**UP-7 (필수) — 하나라도 실패하면 파일을 저장하지 않는다.**

검증 순서를 고정한다. ① 바이트 크기 ② 온전성(UP-2) ③ 매직 바이트 ④ 픽셀 크기
⑤ (가능하면) 재인코딩. 실패 시 저장하지 않고, 임시 파일을 남기지 않는다.
"일단 저장하고 나중에 검사"하는 순서를 만들지 마라.

### 4.4 저장 경로와 파일명

**UP-8 (필수) — 클라이언트 파일명을 사용하지 않는다. 서버가 이름을 생성한다.**

```
파일명 = crypto.randomUUID() + "." + (탐지된 형식의 확장자)
```

원본 파일명은 **저장하지 않는다.** 표시용으로 남기고 싶어도 하지 마라. 원본 파일명에는
사람 이름, 촬영 장소, 클라이언트 이름이 들어 있는 경우가 흔하고, 그것을 화면에 렌더하면
XSS 벡터가 된다.

경로 조작 방어는 3중으로 한다.

1. **구조적 방어** — 경로를 `path.join(BASE_DIR, generatedName)` 으로만 만든다.
   사용자 입력이 경로 조립에 들어가는 지점이 아예 없게 한다. 이것이 본질적 방어다
2. **형식 검증** — 생성된 이름이 `/^[0-9a-f-]{36}\.(jpg|png|webp)$/` 에 매칭되는지 확인한다.
   UUID 생성이므로 항상 통과하지만, 나중에 이름 생성 규칙이 바뀔 때 회귀를 잡는다
3. **격리 확인** — `path.resolve(finalPath)` 가 `path.resolve(BASE_DIR) + path.sep` 로
   시작하는지 확인한다. 아니면 거부한다. 심볼릭 링크나 예상치 못한 정규화까지 잡는다

파일 삭제·교체 기능에서도 **같은 3중 검증을 적용한다.** 삭제는 레코드 id 를 받아
저장된 파일명을 조회해 지우는 방식이어야 하고, 클라이언트가 보낸 파일명이나 경로로
직접 삭제하지 않는다. `../../src/app/page.tsx` 를 지우는 요청이 가능해서는 안 된다.

**UP-9 (권장) — 재인코딩으로 형식을 확정하고 메타데이터를 제거한다.**

디코딩 후 재인코딩하면 "실제로 그 형식의 유효한 이미지"임이 증명되고, EXIF 등 부가
데이터가 함께 사라진다. 가장 확실한 검증이자 메타데이터 처리다.

**`sharp` 패키지가 필요하다. 현재 의존성에 없다.** 네이티브 모듈이라 서버리스 배포에서
플랫폼 바이너리 확인이 필요하다. **패키지 추가는 대표 승인 사항이다.** 승인 전에는
UP-5, UP-6 으로 검증하고 UP-10 으로 EXIF 를 처리한다.

**UP-10 (필수) — EXIF 위치정보를 다룬다.**

스마트폰 사진에는 GPS 좌표, 촬영 일시, 기기 정보가 들어 있다. 코치 사진이나 코칭 공간
사진에 **작업실이나 자택 좌표가 박혀 공개 URL 로 배포되는 상황**이 실제 위험이다.
개인정보보호 문제이기도 하고 개인 안전 문제이기도 하다.

여기서 중요한 함정이 하나 있다. **`next/image` 로 최적화된 출력은 재인코딩되어 메타데이터가
사라지지만, 원본 파일은 여전히 자기 URL 로 직접 다운로드 가능하다.**
`/uploads/xxx.jpg` 를 그대로 요청하면 EXIF 가 붙은 원본이 나온다. 최적화가 EXIF 를
제거해 준다고 생각하면 안 된다.

대응은 우선순위 순으로 셋이다.

1. **UP-9 로 재인코딩** (권장, `sharp` 승인 필요) — 가장 확실하다
2. **JPEG APPn 세그먼트 제거** (권장) — JPEG 한정으로 EXIF/GPS 가 들어 있는 APP1
   세그먼트를 잘라내는 것은 의존성 없이 구현 가능하다. PNG/WebP 는 별도 처리 필요
3. **운영 안내** (필수, 위 둘이 없을 때의 최소선) — 관리자 업로드 화면에
   "사진의 위치정보는 자동으로 제거되지 않습니다. 업로드 전에 확인해 주세요"를 표시하고,
   `docs/admin-architecture.md` 와 DEVNOTE 에 이 한계를 기록한다. **조용히 넘기지 않는다**

3번만 있는 상태로 배포하는 것은 허용하지만, 반드시 명시적으로 기록되어야 한다.

### 4.5 실행 가능한 경로에 놓지 않기

**UP-11 (필수) — 업로드 디렉터리는 정적 자산 전용이어야 한다.**

- `src/app/**` 하위에 쓰지 않는다. 라우트 해석 대상이다
- 프로젝트 루트나 설정 파일 옆에 쓰지 않는다
- 확장자는 UP-1 의 셋만 허용한다. `.js`, `.mjs`, `.ts`, `.json`, `.html`, `.htm`,
  `.svg`, `.php` 는 어떤 경우에도 저장하지 않는다
- 업로드 디렉터리 안에서 코드를 import 하거나 require 하는 코드를 만들지 않는다

Vercel 환경에서 `public/` 은 정적 자산으로만 서빙되고 실행되지 않는다. 이 점은 유리하다.
다만 UP-0 때문에 프로덕션에서 `public/` 에 쓸 수 없다는 문제가 그대로 남는다.

**UP-12 (필수) — 서빙 시 응답 헤더를 통제한다.**

- `X-Content-Type-Options: nosniff` (HDR-2 로 전역 적용)
- `Content-Type` 은 **탐지된 형식** 기준으로 설정한다. 확장자에서 추론한 값을 쓰지 않는다
- 허용 목록 밖의 형식이 어떤 경로로든 서빙되게 되면 `Content-Disposition: attachment` 로
  강제 다운로드시킨다

`nosniff` 가 있으면 `.jpg` 로 저장된 HTML 이 브라우저에서 HTML 로 해석되는 경로가 막힌다.
UP-5 와 함께 이중 방어가 된다.

**UP-13 (권장) — 고아 파일을 정리한다.**

콘텐츠 레코드에서 이미지를 교체하거나 삭제하면 이전 파일이 남는다. 남은 파일은 URL 을
아는 사람에게 계속 노출된다(교체 전 잘못된 이미지가 그대로 접근 가능한 상태). 교체·삭제 시
이전 파일을 함께 삭제하고, 참조되지 않는 파일을 찾는 정리 작업을 둔다.

### 4.6 업로드 전송 경로 — Server Action vs Route Handler

**UP-14 (필수) — Server Action 의 본문 크기 상한을 이해하고 결정한다.**

Server Action 요청 본문은 **기본 1MB** 로 제한된다. 5MB 이미지는 그대로는 못 올라간다.
선택지가 둘이고, 트레이드오프가 다르다.

**선택지 A — `experimental.serverActions.bodySizeLimit` 을 올린다.**

```ts
experimental: { serverActions: { bodySizeLimit: '6mb' } }
```

간단하다. 그런데 이 설정은 **전역**이다. 즉 **공개 상담 폼 액션의 본문 상한도 6MB 로
올라간다.** 인증 없는 엔드포인트가 6MB 요청을 받아 파싱하게 되는 것이고, 이 상한이 본래
DDoS 방어를 위해 존재한다는 점을 생각하면 손해다. 상한은 raw HTTP 본문 기준이며
multipart 경계·헤더 오버헤드(10~20KB)가 포함된다는 점도 감안해야 한다.

**선택지 B — 업로드만 전용 Route Handler 로 분리한다.**

Server Action 상한은 1MB 로 유지하고, 업로드는 `/api/admin/upload` 같은 인증된 Route
Handler 가 스트리밍으로 받는다. 공개 액션의 상한이 그대로 유지되고 업로드 크기를 독립적으로
통제할 수 있다. 대신 **Server Action 의 자동 CSRF 보호가 적용되지 않으므로 직접 처리해야
하고**(CSRF-2), P4 에 따라 핸들러 내부 인증이 필수다.

**내 권장은 B 다.** 공개 엔드포인트의 방어 수준을 관리자 편의 때문에 낮추는 것이 이 사이트
구조에서 더 나쁘다. 다만 이건 아키텍처 결정이므로 **데이브가 `docs/admin-architecture.md`
에서 최종 판단**하고, B 를 고르면 CSRF-2 를, A 를 고르면 공개 액션의 별도 크기 검증을
반드시 함께 넣어야 한다.

## 5. 검색엔진 노출 차단

**SEO-1 (필수) — `X-Robots-Tag` 헤더로 관리자 경로를 차단한다.**

`next.config.ts` 의 `headers()` 에서 `/admin/:path*` 에 다음을 설정한다.

```
X-Robots-Tag: noindex, nofollow, noarchive, nosnippet
```

헤더 방식을 **주 수단**으로 쓰는 이유는, HTML 이 아닌 응답(JSON, 파일 다운로드)까지
덮고, 페이지 메타데이터 설정을 빠뜨린 라우트도 함께 덮이기 때문이다.
`next.config.ts` 의 `headers` 는 파일시스템 라우트보다 먼저 검사되므로 적용 범위가 넓다.

P2 와 같은 함정이 있다. `source: '/admin/:path*'` 는 `/admin` 정확히를 놓친다.
`/admin` 과 `/admin/:path*` 를 모두 나열해라.

**SEO-2 (권장) — 관리자 레이아웃에 메타데이터로도 표시한다.**

```ts
export const metadata = { robots: { index: false, follow: false } }
```

헤더가 있으면 중복이지만, 헤더 설정이 실수로 빠질 때의 안전망이다. 로그인 페이지에도 넣는다.

**SEO-3 (필수) — `app/robots.ts` 에 `/admin` 을 disallow 한다.**

```ts
rules: { userAgent: '*', allow: '/', disallow: ['/admin', '/admin/'] }
```

여기서 트레이드오프를 짚는다. `robots.txt` 는 공개 파일이므로 **관리자 경로를 세상에
알려주는 셈**이다. 그런데 `/admin` 은 애초에 추측 가능한 경로이고, **경로의 비밀성을 보안
수단으로 취급해서는 안 된다.** 보안은 인증(1절)이 담당한다. 반대로 disallow 를 빼면
어딘가에서 링크가 걸릴 때 색인될 위험이 남는다. 표기하는 편이 낫다.

경로를 숨기고 싶다면 `robots.txt` 에 넣지 않고 SEO-1 의 헤더만 쓰는 것도 가능하다.
그 경우 크롤러가 페이지를 요청하기는 하지만 색인하지 않는다. 어느 쪽이든 **인증이 실제
방어선**이라는 점은 같다.

**SEO-4 (필수) — `sitemap.ts` 는 명시적 허용 목록으로 만든다.**

파일시스템을 훑어 라우트를 자동 생성하는 방식을 쓰지 마라. 관리자 라우트가 자동으로
포함되고, 앞으로 라우트를 추가할 때마다 같은 위험이 생긴다. 공개 라우트를 손으로 나열한다.
`/` 와 `/privacy` 가 들어가고, `/admin*` 은 들어가지 않는다.

**SEO-5 (필수) — 공개 페이지에서 관리자 페이지로 링크하지 않는다.**

푸터에 "관리자" 링크를 넣지 않는다. 크롤러가 링크를 따라가고, `robots.txt` 의 disallow 는
색인을 완전히 막아주지 않는다. 대표는 URL 을 직접 입력하거나 북마크를 쓴다.

**SEO-6 (권장) — 관리자 경로의 `Referrer-Policy` 를 `no-referrer` 로 둔다.**

관리자 화면에서 외부 링크를 클릭하면 기본 정책에서는 오리진이 전달된다. 관리자 경로는
`no-referrer` 로 두어 경로나 오리진이 외부로 새지 않게 한다. 공개 페이지는
`strict-origin-when-cross-origin` 을 쓴다(HDR-4).

## 6. 공개 폼 남용 방어 · CSRF · 보안 헤더

### 6.1 상담 폼 rate limit · 스팸 방어

1.4 와 같은 제약이 그대로 적용된다. **서버리스에서 공유 카운터 없이 정확한 rate limit 은
불가능하다.** 대신 봇 트래픽 대부분을 걸러내는 저비용 수단이 있다. 그리고 이 폼은
전환 지점이므로 **과한 차단이 매출 손실**이라는 점도 함께 고려해야 한다.

**RATE-1 (필수) — 허니팟 필드를 둔다.**

시각적으로 숨긴 입력 필드(예: `company_website`)를 두고, 값이 있으면 조용히 거부한다.
자동 폼 채우기 봇 상당수가 걸린다.

구현 주의사항 둘. `type="hidden"` 을 쓰지 마라 — 봇이 hidden 을 건너뛴다. CSS 로
화면 밖에 배치하되 `aria-hidden="true"` 와 `tabindex="-1"` 을 붙여 스크린리더와 키보드
사용자에게 노출되지 않게 한다. **시니어 대상 사이트라 접근성이 특히 중요하다.**
선우와 함께 구현해라. 그리고 거부할 때 에러를 보여주지 말고 성공 화면을 보여준다.
봇에게 실패를 알려줄 이유가 없다.

**RATE-2 (필수) — 폼 렌더 시각을 서명해서 넣고 제출 간격을 검증한다.**

폼 렌더 시 `renderedAt` 타임스탬프와 그것의 HMAC 을 hidden 으로 내려보내고, 제출 시
서명을 검증한 뒤 경과 시간을 본다.

- **2초 미만**: 사람이 이 폼을 채울 수 없는 시간이다. 거부
- **2시간 초과**: 만료. "다시 시도해 주세요"로 안내하고 재렌더

서명이 있어야 하는 이유는 값이 클라이언트에 있기 때문이다. 서명이 없으면 봇이 값을
바꿔 검증을 우회한다. 서명 키는 `ADMIN_SESSION_SECRET` 과 **다른 값**을 쓰거나, 같은
키를 쓰되 메시지에 용도 접두어(`form:`)를 넣어 도메인을 분리해라. 같은 키를 용도 구분 없이
쓰면 한쪽 서명을 다른 쪽에 재사용하는 공격이 가능해진다.

정적 프리렌더와 충돌한다는 점을 유의해라. `renderedAt` 을 서버에서 생성하면 폼을 포함한
페이지가 동적이 된다. 현재 `/` 는 정적 프리렌더되고 있다(DEVNOTE 8절). 해결책은
**폼 컴포넌트만 동적 경계 안에 두는 것**이다(Suspense 경계 + 서버 컴포넌트로 토큰 발급).
선우·데이브와 조율할 지점이다. 이 요건이 랜딩 페이지 전체를 동적으로 만들어서는 안 된다.

**RATE-3 (필수) — 필드 길이 상한을 서버에서 강제한다.**

PII-3 의 표를 따른다. 남용 방어와 저장소 보호를 겸한다. 상한이 없으면 JSON 파일이
무한히 커지고, 관리자 화면 렌더가 무너진다.

**RATE-4 (필수) — 중복 제출을 흡수한다.**

같은 정규화된 연락처로 10분 내 재접수가 오면 새 레코드를 만들지 않고 성공 화면을
보여준다. 더블클릭이나 재시도로 같은 사람이 여러 건 쌓이는 것을 막는다. 판단 기준은
저장된 레코드이므로 추가 인프라가 없다.

**RATE-5 (권장) — Vercel WAF 의 rate limit 규칙을 상담 폼 경로에 설정한다.**

AUTH-15 와 같다. 플랫폼 엣지 제한만이 서버리스 우회에 강하다. **Vercel 계정이 없어
지금은 불가능하다.** 첫 배포 직후 작업 항목이다.

**RATE-6 (나중) — 캡차(Cloudflare Turnstile, hCaptcha)는 지금 넣지 않는다.**

이유가 셋이다. 외부 서비스 계정이 하나 더 늘어나고, 그 계정도 신규 개설 정책 대상이라
대표 승인이 필요하다. 스크립트를 하나 더 로드하므로 CSP 를 넓혀야 한다. 그리고
**시니어 사용자에게 캡차는 실질적인 진입 장벽**이다. 실제 스팸이 관측된 뒤에 도입한다.
관측 없이 미리 넣지 않는다.

### 6.2 CSRF

**CSRF-1 (필수) — Server Action 을 쓰는 경우 별도 CSRF 토큰이 필요하지 않다. 판단 근거를 남긴다.**

Next.js 는 Server Action 요청의 `Origin` 을 `Host`(또는 `X-Forwarded-Host`)와 비교하고
불일치하면 거부한다. 프레임워크 수준의 CSRF 방어다. 여기에 세션 쿠키의
`SameSite=Strict`(AUTH-6)가 더해지면, 교차 사이트에서 유발된 요청에는 쿠키가 아예 붙지
않는다. 이중 방어다.

**결론: Server Action 기반 관리자 변경 작업에 CSRF 토큰을 추가하지 않는다.**
직접 만든 토큰은 검증 누락 지점을 만들 뿐이다.

**단, 두 가지를 지켜야 성립한다.**

- **`experimental.serverActions.allowedOrigins` 를 설정하지 않는다.** 이 옵션은 허용
  오리진을 **넓히는** 설정이다. 프록시나 CDN 도메인이 필요한 특수한 경우에만 쓴다.
  이 사이트에는 필요 없다. 값이 들어가면 CSRF 보호가 그만큼 약해진다
- **관리자 변경 작업을 GET 으로 만들지 않는다.** 삭제·저장을 링크(`<a href>`)로 만들면
  프레임워크 보호가 적용되지 않는다. 전부 form submit 또는 액션 호출이어야 한다

**CSRF-2 (필수) — Route Handler 를 쓰면 CSRF 를 직접 처리한다.**

UP-14 에서 선택지 B(업로드 전용 Route Handler)를 고르면 Server Action 의 자동 CSRF 검사가
적용되지 않는다. 핸들러에서 직접 확인한다.

- `Origin` 헤더가 자기 오리진과 일치하는지 확인. 없거나 다르면 거부
- 또는 `Sec-Fetch-Site: same-origin` 을 확인
- `SameSite=Strict` 쿠키가 이미 상당 부분 막지만, 헤더 확인을 생략하지 않는다
- `GET` 으로 변경 작업을 노출하지 않는다. 업로드 핸들러는 `POST` 만 export 한다

**CSRF-3 (권장) — `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 를 고정한다.**

Next.js 는 인라인 액션이 캡처한 클로저 변수를 암호화해 클라이언트로 보낸다. 여러 인스턴스에
배포될 때 이 키가 인스턴스마다 다르면 복호화가 실패한다. 안정적인 값을 환경변수로 설정한다.
배포 간 액션 ID 변경으로 "Failed to find Server Action" 이 발생할 수 있다는 점은
선우가 UI 에서 재시도 안내로 처리하면 된다(AUTH-18 과 같은 성격).

### 6.3 보안 헤더

`next.config.ts` 는 현재 비어 있다. 아래를 `headers()` 로 설정한다.
`next.config.ts` 의 `headers` 는 proxy 보다 먼저, 파일시스템 라우트보다 먼저 검사되므로
정적 파일에도 적용된다. 이 점이 유리하다.

**전체 경로 (`/:path*`)**

| ID | 헤더 | 값 | 우선순위 |
| --- | --- | --- | --- |
| HDR-1 | `Strict-Transport-Security` | `max-age=63072000; includeSubDomains` | 필수 |
| HDR-2 | `X-Content-Type-Options` | `nosniff` | 필수 |
| HDR-3 | `X-Frame-Options` | `DENY` | 필수 |
| HDR-4 | `Referrer-Policy` | `strict-origin-when-cross-origin` | 필수 |
| HDR-5 | `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=(), usb=()` | 필수 |
| HDR-6 | `Cross-Origin-Opener-Policy` | `same-origin` | 권장 |
| HDR-7 | `Content-Security-Policy` | 6.4 참조 | 필수(부분) |

**HDR-8 (필수) — `poweredByHeader: false` 를 설정한다.**

`X-Powered-By: Next.js` 는 버전 특정 공격에 정보를 준다. 설정 한 줄이다.

**HDR-9 (필수) — 관리자 경로에 추가 헤더를 적용한다.**

| 헤더 | 값 | 이유 |
| --- | --- | --- |
| `Cache-Control` | `no-store, must-revalidate` | PII-17. 상담 데이터가 캐시에 남지 않게 |
| `X-Robots-Tag` | `noindex, nofollow, noarchive, nosnippet` | SEO-1 |
| `Referrer-Policy` | `no-referrer` | SEO-6 |

`source` 에 `/admin` 과 `/admin/:path*` 를 모두 나열해라(P2 와 같은 함정).

**HDR-1 주의: `preload` 를 지금 붙이지 마라.** HSTS preload 목록 등재는 되돌리기 매우
어렵다. 모든 서브도메인이 HTTPS 로 서비스된다는 것이 확인된 뒤에 검토한다. 도메인이
아직 확정되지 않은 상태에서 붙일 결정이 아니다. Vercel 은 `*.vercel.app` 도메인에
HSTS 를 자체 설정하지만, 커스텀 도메인에서는 직접 설정해야 한다.

### 6.4 CSP — 이미지 업로드·인라인 스타일과의 충돌

CSP 는 이 프로젝트에서 가장 조심해야 할 헤더다. 잘못 넣으면 사이트가 깨지고, 느슨하게
넣으면 있는 척만 하게 된다. 충돌 지점을 먼저 나열한다.

**충돌 1 — nonce 방식은 정적 렌더링을 포기해야 한다.**

nonce 는 요청마다 새로 생성되어야 하므로 **모든 페이지가 동적 렌더링**이어야 한다.
공식 문서가 명시한다 — 정적 최적화와 ISR 이 비활성화되고, CDN 캐싱이 안 되고, PPR 과
호환되지 않는다. 현재 `/` 는 정적 프리렌더되고 있다(DEVNOTE 8절). nonce CSP 를 전역
적용하면 그 이점을 잃는다.

**충돌 2 — framer-motion 의 인라인 style 속성은 nonce 로 허용할 수 없다.**

이건 놓치기 쉬운 지점이라 정확히 적는다. nonce 는 `<style>` **요소**에 붙일 수 있지만
`style="..."` **속성**에는 붙일 수 없다. 속성은 `style-src-attr` 이 관장한다.
framer-motion 은 애니메이션을 인라인 style 속성으로 적용하므로,
`style-src 'self' 'nonce-X'` 만 두면 **모든 애니메이션이 깨진다.**

따라서 nonce 방식을 쓰려면 이렇게 되어야 한다.

```
style-src 'self' 'nonce-X';
style-src-attr 'unsafe-inline';
```

`style-src-attr 'unsafe-inline'` 은 CSS 주입 위험을 남기지만 스크립트 실행과는 급이 다르다.
framer-motion 을 쓰는 한 실질적으로 대안이 없다. `next/font` 가 주입하는 `<style>` 요소에는
Next.js 가 nonce 를 자동으로 붙여준다.

**충돌 3 — 이미지 업로드 미리보기는 `blob:` 이 필요하다.**

선택한 파일을 미리보기하려면 `URL.createObjectURL()` 로 `blob:` URL 을 만든다.
`img-src` 에 `blob:` 이 없으면 미리보기가 표시되지 않는다. `FileReader` 의 data URL 을
쓴다면 `data:` 도 필요하다. **`blob:` 을 쓰고 `data:` 는 가능하면 넣지 마라.**
data URL 허용은 필요 이상으로 표면을 넓힌다.

나중에 Supabase Storage 로 이미지를 옮기면 그 오리진을 `img-src` 에 추가해야 한다.
그때 이 문서를 갱신해라.

**충돌 4 — Server Action 은 same-origin fetch 다.** `connect-src 'self'` 로 충분하다.
`form-action 'self'` 도 문제없다.

**이 충돌들을 감안한 권장안: 경로별로 다른 정책을 쓴다.**

관리자 페이지는 쿠키를 읽으므로 **어차피 동적**이다. nonce 의 비용이 0 이다.
공개 랜딩은 정적 렌더링을 유지해야 한다. 그래서 이렇게 나눈다.

**CSP-1 (필수) — 공개 경로: 스크립트 외 지시어를 `next.config.ts` 에서 적용한다.**

```
default-src 'self';
script-src 'self' 'unsafe-inline';
style-src 'self' 'unsafe-inline';
img-src 'self' blob: data:;
font-src 'self';
object-src 'none';
base-uri 'self';
form-action 'self';
frame-ancestors 'none';
upgrade-insecure-requests;
```

**`script-src` 에 `'unsafe-inline'` 이 있으므로 이 정책은 XSS 를 막지 못한다.**
솔직하게 적는다. 그래도 넣는 이유는 나머지 지시어들이 각각 실질적 가치가 있기 때문이다.
`object-src 'none'` 은 플러그인 기반 공격을, `base-uri 'self'` 는 `<base>` 태그 주입으로
상대 경로 스크립트를 탈취하는 공격을, `frame-ancestors 'none'` 은 클릭재킹을,
`form-action 'self'` 는 폼 전송 대상 변조를 막는다. 정적 렌더링을 유지하면서 얻을 수 있는
부분이다.

**CSP-2 (필수) — 관리자 경로: `proxy.ts` 에서 nonce 기반 정책을 적용한다.**

```
default-src 'self';
script-src 'self' 'nonce-{생성값}' 'strict-dynamic';
style-src 'self' 'nonce-{생성값}';
style-src-attr 'unsafe-inline';
img-src 'self' blob:;
font-src 'self';
object-src 'none';
base-uri 'self';
form-action 'self';
frame-ancestors 'none';
upgrade-insecure-requests;
```

개발 환경에서는 `script-src` 에 `'unsafe-eval'` 이 필요하다(React 가 디버깅 정보를 위해
`eval` 을 쓴다). `process.env.NODE_ENV === 'development'` 로 분기한다. **프로덕션에
`'unsafe-eval'` 이 들어가지 않는 것을 확인해라.**

nonce 를 붙이는 proxy 의 matcher 는 **인증 matcher 와 별개**여야 한다(P10).
CSP 부착에는 프리페치 제외 조건을 쓸 수 있지만 인증에는 쓸 수 없다.

**CSP-3 (권장) — 공개 경로도 strict CSP 로 옮기는 것을 검토한다.**

두 가지 경로가 있다.

- `experimental.sri`(하드코딩된 해시 기반 CSP)를 쓰면 정적 생성을 유지하면서 `'unsafe-inline'`
  없는 `script-src` 가 가능하다. **실험 기능**이라 프로덕션 의존은 신중해야 한다
- 랜딩 페이지도 동적으로 전환하고 nonce 를 적용한다. 성능·비용 손실을 감수하는 선택이다

지금 결정하지 않는다. 랜딩 페이지에 사용자 입력이 렌더되지 않는 한(현재 그렇다) XSS
표면이 크지 않다. **다만 관리자에서 편집한 콘텐츠가 공개 페이지에 렌더되기 시작하면
상황이 바뀐다** — 그 콘텐츠가 신뢰 경계를 넘어온 데이터이기 때문이다. 아래를 지켜라.

**CSP-4 (필수) — 관리자가 입력한 콘텐츠를 HTML 로 렌더하지 않는다.**

`dangerouslySetInnerHTML` 을 쓰지 않는다. React 의 기본 텍스트 렌더링(자동 이스케이프)만
쓴다. 마크다운이나 리치텍스트 편집기를 넣고 싶어지면 그때 새니타이저 요건을 다시 정의해야
한다. 지금은 평문만 허용한다.

이유는 관리자 계정이 뚫렸을 때의 피해 범위다. 콘텐츠에 HTML 이 들어갈 수 있으면
공격자는 **모든 방문자에게 스크립트를 배포**할 수 있다. 평문만 허용하면 피해가 문구 훼손에
그친다.

`site.ts` 의 링크 필드(`href`)도 주의 대상이다. 관리자가 편집 가능해지면
`javascript:` 스킴을 넣을 수 있다. **`href` 값은 `https://`, `http://`, `/`, `#`,
`mailto:`, `tel:` 로 시작하는 것만 허용하는 화이트리스트 검증이 필요하다.**

### 7.3 의존성 점검

**DEP-1 (필수) — `npm audit` 을 배포 전에 실행하고 결과를 DEVNOTE 에 기록한다.**

`npm install` 시 `--cache F:\_npm-cache` 를 붙이는 규칙은 `AGENTS.md` 에 있다.
`npm audit` 은 설치를 하지 않으므로 캐시 문제와 무관하다.

**DEP-2 (필수) — 새 패키지 도입은 승인 사항이다.**

이 문서에서 새 패키지가 필요한 항목은 둘이다.

- `sharp` — UP-9 (재인코딩 + EXIF 제거). 네이티브 모듈, 서버리스 배포 확인 필요
- 스키마 검증 라이브러리(`zod` 등) — PII-3. 직접 작성한 검증 함수로도 요건은 충족된다

둘 다 없이 배포 가능하다. 다만 UP-9 가 없으면 EXIF 가 원본에 남는다는 사실을 UP-10 의
3번(운영 안내)으로 처리해야 한다.

## 8. 이번 배포를 막아야 하는 조건

아래 중 **하나라도 해당하면 배포하지 않는다.** 순서는 심각도 순이다.

### 치명 — 개인정보 관련 법적 의무 미이행

1. **상담 폼 전송이 활성화되었는데 `/privacy` 페이지가 없다.**
   개인정보를 수집하면서 처리방침을 공개하지 않는 상태다. 게시 의무 위반이며 과태료
   대상이다 (PRIV-1)

2. **처리방침에 플레이스홀더 값이 남아 있다.**
   `○○○`, `000-00-00000`, `hello@example.com`, `070-0000-0000` 이 게시되면 법정
   고지사항이 허위가 된다. 대표에게서 실제 값을 받기 전에는 게시하지 않는다 (PRIV-3, PRIV-4)

3. **개인정보 보호책임자의 실명과 연락처가 처리방침에 없다.** (PRIV-3)

4. **동의 문구와 실제 수집 항목이 다르다.**
   현재 상태가 그렇다. 문구는 "이름·연락처"만 말하는데 폼은 희망시간·고민을 받는다.
   트랙 필드가 추가되면 하나 더 늘어난다 (CONS-1)

5. **파기 시점이 결정론적으로 정의되지 않았다.**
   "상담 종료 후 6개월"만으로는 미상담 건의 파기 시점이 없다. 무기한 보관 상태가 되고
   제21조 위반이다 (PII-9, PII-10)

6. **자동 파기가 어떤 형태로도 동작하지 않는다.**
   최소한 지연 파기(PII-11 의 1번)가 동작해야 한다. 수동 삭제 버튼만으로는 약속한
   파기를 이행한다고 볼 수 없다

7. **상담 데이터 파일이 `.gitignore` 에 없거나, `public/` 하위에 있다.**
   git 커밋은 되돌리기 어렵고 이 저장소는 곧 새 GitHub 계정으로 push 될 예정이다.
   `public/` 은 인증을 통과하지 않는다 (PII-6, P6)

### 치명 — 인증 우회

8. **`requireAdmin()` 없이 실행되는 관리자 Server Action 이나 Route Handler 가 하나라도 있다.**
   proxy 만으로는 막히지 않는다. Server Function 은 그것을 쓰는 페이지 라우트의 POST 로
   처리되므로 matcher 제외가 그대로 우회 경로가 된다 (P3, P4)

9. **세션 쿠키 값이 서명·검증되지 않는다.** 위조가 자유롭다 (AUTH-4, AUTH-5)

10. **관리자 페이지가 정적 프리렌더된다.** (P8)

11. **환경변수가 없을 때 인증을 건너뛰는 분기가 존재한다.** (AUTH-14)

12. **`ADMIN_PASSWORD_HASH` 대신 평문 비밀번호를 환경변수에 둔다.** (AUTH-1)

13. **관리자 비밀번호가 사람이 만든 문구다.**
    서버리스에서 신뢰할 수 있는 시도 제한이 불가능하므로, 엔트로피가 실질적인 유일한
    방어선이다. 난수 20자 이상이 아니면 배포하지 않는다 (AUTH-9)

### 치명 — 저장 자체가 성립하지 않음

14. **Vercel 에 배포하면서 파일시스템 저장소를 쓴다.**
    런타임 파일시스템이 읽기 전용이다. **상담 신청이 저장되지 않는다.** 최악의 형태는
    폼이 "접수되었습니다"를 보여주면서 데이터가 사라지는 것이다. 사용자는 연락을 기다리고
    대표는 신청이 없다고 생각한다. 신뢰 문제이자 사실상의 데이터 유실이다.

    해결 없이는 배포하지 않는다. 선택지는 셋이다.
    - 로컬·자체 호스팅에서만 운영하고 Vercel 배포를 보류한다
    - 저장소 어댑터를 Supabase(또는 다른 관리형 저장소)로 교체한 뒤 배포한다.
      **새 Supabase 계정 개설이 필요하고 이는 대표가 직접 해야 한다.** RLS 를 먼저 켜고
      `service_role` 키가 클라이언트로 내려가지 않는 것을 확인해야 한다. 그때 나에게
      다시 검토를 요청해라
    - 상담 폼 전송을 비활성화한 상태로 배포한다(현재의 가짜 완료 화면을 유지하되,
      **"현재 온라인 신청은 준비 중입니다. 전화로 문의해 주세요"로 정직하게 표시**한다)

15. **이미지 업로드가 프로덕션에서 성공한 것처럼 보이지만 실제로 저장되지 않는다.**
    같은 문제다. 프로덕션에서 기능을 명시적으로 비활성화하고 UI 에 안내하거나, blob
    스토리지를 붙일 때까지 보류한다 (UP-0)

### 높음 — 배포 전 반드시 처리

16. **SVG 업로드가 허용된다.** 저장형 XSS 경로다 (UP-3)

17. **업로드 파일 내용 검증이 없다.** 확장자·MIME 만 확인하는 상태 (UP-5)

18. **업로드 경로 조립에 사용자 입력이 들어간다.** (UP-8)

19. **보안 헤더가 하나도 설정되지 않았다.** `next.config.ts` 가 비어 있는 현재 상태.
    최소한 HDR-1~5, HDR-8, HDR-9 (PII-17, SEO-1)

20. **관리자 경로가 `X-Robots-Tag` 로 차단되지 않는다.** (SEO-1)

21. **함수 로그나 에러 응답에 이름·연락처가 남는다.**
    Vercel 로그는 플랫폼에 보관되므로 사실상 제3자 이전이다 (LOG-1, LOG-3)

22. **관리자 목록이 연락처를 전부 노출한다.** (PII-14)

23. **호스팅 사업자가 처리방침의 수탁자에 기재되지 않았거나, 국외이전 여부가 확인되지 않았다.**
    리전 선택은 계정 개설 시점에 결정해야 하고, 나중에 바꾸면 데이터 이전 작업이 된다
    (PRIV-5, PRIV-6)

24. **`dangerouslySetInnerHTML` 로 관리자 입력 콘텐츠를 렌더한다.** (CSP-4)

### 확인이 필요한 항목 (배포 차단은 아니나 명시적 결정이 필요)

25. **[법률 검토 필요] 로 표시한 항목들이 검토되지 않았다.**
    특히 (a) 자유 입력란의 민감정보 처리 근거 (PII-1), (b) 필수·선택 동의 분리 방식
    (CONS-4), (c) 동의 거부 권리 고지 문구 (CONS-3), (d) 국외이전 동의 필요 여부
    (PRIV-6), (e) 접속기록 보관 의무의 적용 범위 (PII-16), (f) 만 14세 미만 고지만으로
    충분한지 (PII-5). 나는 변호사가 아니고 이 판단을 대신할 수 없다.
    **배포 여부는 대표가 위험을 인지한 상태에서 결정할 사안이다.** 검토 없이
    "괜찮을 것"으로 넘기지 마라

26. **UP-9(재인코딩)가 없어 EXIF 위치정보가 원본에 남는 상태.**
    UP-10 의 3번(운영 안내)이 있으면 배포 가능하다. 안내조차 없으면 안 된다
